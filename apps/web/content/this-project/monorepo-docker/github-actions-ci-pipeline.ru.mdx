## 1. Анатомия GitHub Actions: из чего состоит наш CI/CD

Весь пайплайн описан в `.github/workflows/ci.yml` и опирается на переиспользуемый **Composite Action** (`.github/actions/setup-workspace/action.yml`) и граф задач `turbo.json`. Главная идея для понимания GitHub Actions: **каждый `job` запускается на отдельной чистой виртуальной машине (`ubuntu-latest`)** со своей файловой системой и оперативной памятью.

### Ключевые секции и поля `.github/workflows/ci.yml`

| Поле YAML | Назначение и что делает в нашем проекте |
| :--- | :--- |
| **`on:`** | Триггеры запуска: `push` в `main`, `pull_request` (в целевую ветку `main`) и ручной `workflow_dispatch` (кнопка *Run workflow* в UI GitHub). |
| **`permissions:`** | Выдаёт временному токену `GITHUB_TOKEN` минимальные права (принцип Least Privilege): только `contents: read` (чтение кода без права пуша или изменения релизов). |
| **`concurrency:`** | Управляет параллельными запусками одного workflow: отменяет устаревшие проверки внутри одного PR и защищает каждый коммит в `main`. |
| **`env:`** | Переменные окружения на весь workflow (`CI: true`, `LEFTHOOK: 0`, отключение телеметрии `DO_NOT_TRACK`, `TURBO_TELEMETRY_DISABLED`, `NEXT_TELEMETRY_DISABLED`). |
| **`jobs.<id>.runs-on:`** | Выбор образа виртуальной машины (`ubuntu-latest`). |
| **`jobs.<id>.needs:`** | Задаёт порядок (граф зависимостей). Например, `needs: [ lint, typecheck ]` не запустит `build`, пока оба родителя не завершатся успешно. |
| **`name:` / `id:`** | `name:` — человекочитаемое имя шага/джобы в UI GitHub; `id:` — технический идентификатор шага для чтения `${{ steps.<id>.outputs.* }}`. |
| **`if:`** | Условие запуска шага или джобы (например, `if: inputs.prepare-codegen == 'true'` или `if: failure()` для выгрузки логов). |
| **`steps` (`uses:` vs `run:`)** | `uses:` запускает готовый экшен (из Marketplace или локальной папки `./.github/actions/...`), а `run:` выполняет bash-команду на раннере. |
| **`${{ ... }}` контексты** | Динамические переменные от GitHub: `github.event_name` (`push` или `pull_request`), `github.sha`, `github.event.pull_request.base.sha`, `runner.os`. |

### `inputs` и `outputs`: как шаги и джобы обмениваются данными

Поскольку в GitHub Actions нельзя просто объявить общую JS-переменную для всего файла, для обмена параметрами используются **инпуты (`inputs`)** и **аутпуты (`outputs`)**:

1. **Внутри Composite Action (`action.yml`) — параметризация переиспользуемого блока:**
   - **`inputs:`** — аргументы, которые вызывающий job передаёт внутрь через `with:`. У нас в `setup-workspace` это `prepare-codegen` (`required: false`, `default: "false"`): job `typecheck` передаёт `"true"`, а остальные оставляют `"false"`.
   - **`outputs:`** — значения, которые шаг внутри экшена может вернуть наружу (через запись в `$GITHUB_OUTPUT`), чтобы использовать их в следующих шагах того же job.
2. **Между разными `jobs` (на уровне разных VM):**
   - Так как у каждой джобы своя виртуальная машина, передать строку (например, собранный тег Docker-образа, URL превью-деплоя или флаг `has-changes`) из `job_a` в `job_b` можно через `jobs.job_a.outputs`:
     1. Внутри `job_a` шаг с `id: meta` пишет `echo "tag=v1.2.3" >> "$GITHUB_OUTPUT"`.
     2. На уровне `job_a` объявляется `outputs: { tag: ${{ steps.meta.outputs.tag }} }`.
     3. В `job_b` ставится `needs: [ job_a ]` и значение читается через `${{ needs.job_a.outputs.tag }}`.
   - Для тяжёлых файлов (сборки `.next`, скриншоты Playwright) вместо `outputs` (они годятся только для коротких строк) используют **`actions/upload-artifact`** и **`actions/download-artifact`**.

> [!NOTE]
> **Три уровня переиспользования в GitHub Actions:** одиночные шаги оформляются как **Composite Action** (`uses: ./.github/actions/...`), готовые сторонние шаги берутся из Marketplace (`uses: actions/checkout@v6`), а повторяющиеся целиком джобы или CD-пайплайны выносятся в **Reusable Workflows** (`on: workflow_call`).

## 2. Граф задач (DAG) и почему выбраны 5 отдельных Jobs

Вместо одного длинного скрипта проверки выстроены в **двухступенчатый направленный ациклический граф (DAG)**, куда без переделок встраиваются будущие автотесты:

```text
Stage 1 (Параллельный Fail-Fast и граф типов)     Stage 2 (Тяжёлые сборки после гейтов)
──────────────────────────────────────────────     ─────────────────────────────────────
[lint] (Biome 2.6, shallow) ──────────────────┐
                                              ├──▶ [build] (Turborepo + .turbo + .next/cache)
[typecheck] (tsc + prepare-codegen) ──────────┤
                                              └──▶ [storybook] (@repo/ui build-storybook)
[security] (Compose + pnpm audit, без install) ──▶ Независимый supply-chain шлюз

Слоты под расширение (без перестройки DAG):
[unit-tests] (Vitest) ───────────────────────────▶ Параллельно Stage 1 (рядом с lint / typecheck)
[e2e] (Playwright + Chromium) ───────────────────▶ Stage 2/3 с needs: [ lint, typecheck, build ]
```

### Профили всех 5 Jobs

| Job | Зависимости (`needs`) | Git `fetch-depth` | Ставит `node_modules`? | Команда (`pull_request` vs `main`) |
| :--- | :--- | :--- | :--- | :--- |
| **`lint`** | — | `'1'` (shallow) | Да (без кодогенерации) | `pnpm run lint` (`biome check .` по всему репозиторию за ~150 мс) |
| **`security`** | — | `'1'` (shallow) | **Нет** | `docker compose config --quiet` → `pnpm audit --prod --audit-level=high` |
| **`typecheck`** | — | PR: `'0'`, `main`: `'1'` | Да + `prepare-codegen` | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run typecheck` |
| **`build`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Да | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run build` |
| **`storybook`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Да | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `turbo run build-storybook` |

### Почему Multi-Job DAG лучше одного монолитного Job

Объединение всех команд в один общий job экономит ~15–30 секунд на старте виртуальных машин (`checkout` + `setup-workspace`), но мы **осознанно выбрали** модульный граф:

1. **Готовые слоты под `Vitest` и `Playwright` E2E:** быстрые unit-тесты встают в Stage 1 параллельно `typecheck`, а тяжёлый браузерный `Playwright` подключается после `build` со своим кэшем Chromium и БД, не тормозя `lint`, `security` и `storybook`.
2. **Мгновенный Fail-Fast и экономия сборок:** в PR Checks сразу видно, какой контур упал (`Lint`, `Security`, `Typecheck`, `Build` или `Storybook`), а `needs: [ lint, typecheck ]` физически не даёт запускать сборки Next.js и Storybook, если сломан синтаксис или типы TypeScript.
3. **Разделение прав и изоляция `node_modules`:** `security` вообще не ставит `node_modules` и не исполняет скрипты пакетов, а `lint` и `security` скачивают только последний коммит (`fetch-depth: 1`).
4. **Атомарные обязательные проверки (Branch Protection):** каждый job выступает отдельным Required Status Check перед мерджем в `main`.
5. **Независимый сигнал по безопасности:** `security` не блокирует `build` и `storybook` — при выходе нового CVE в сторонней библиотеке разработчик всё равно видит, собирается ли код.

## 3. DRY-инициализация воркспейса (`.github/actions/setup-workspace/action.yml`)

Чтобы не дублировать настройку `pnpm`, `Node.js 22` и кэша стора в 4+ джобах, вся подготовка вынесена в локальный Composite Action:

```yaml title=".github/actions/setup-workspace/action.yml"
inputs:
  prepare-codegen:
    description: Build @repo/shared-schemas and generate Prisma Client before typecheck
    required: false
    default: "false"

runs:
  using: composite
  steps:
    - name: Setup pnpm
      uses: pnpm/action-setup@v5

    - name: Setup Node.js
      uses: actions/setup-node@v6
      with:
        node-version: "22"
        cache: pnpm

    - name: Install dependencies
      shell: bash
      run: pnpm install --frozen-lockfile

    - name: Prepare generated types (@repo/shared-schemas, Prisma Client & Next.js routes)
      if: inputs.prepare-codegen == 'true'
      shell: bash
      run: |
        pnpm --filter @repo/shared-schemas build
        pnpm --filter @repo/api prisma:generate
        pnpm --filter @repo/web exec next typegen
```

Ключевые детали реализации:

- **Порядок `pnpm/action-setup@v5` до `actions/setup-node@v6`:** настройка `cache: pnpm` требует уже доступного бинарника `pnpm`, чтобы определить путь к стору. Версия не дублируется в YAML — экшен читает `"packageManager": "pnpm@12.18.0"` из корневого `package.json`.
- **Единый runtime без устаревших версий:** мажорные версии `actions/checkout@v6`, `actions/setup-node@v6`, `actions/cache@v5` и `pnpm/action-setup@v5` работают на современном Node 24 runtime для Actions.
- **`pnpm install --frozen-lockfile` с белым списком `allowBuilds`:** в отличие от продакшен-Dockerfiles (`--ignore-scripts`), в CI разрешённым пакетам (`@prisma/client`, `@swc/core`, `@biomejs/biome`) нужно скомпилировать бинарники. Безопасность гарантируется `allowBuilds` в `pnpm-workspace.yaml` — любые неизвестные `postinstall`-скрипты по умолчанию заблокированы.
- **`LEFTHOOK: 0` и отключение телеметрии:** глобальная `LEFTHOOK: 0` отключает установку локальных git-хуков скриптом `prepare` внутри эфемерного раннера.

## 4. `concurrency` без потери коммитов в ветке `main`

Тонкость GitHub Actions: в одной `concurrency`-группе хранится максимум **1 выполняющийся + 1 ожидающий** прогон. Статичная группа вроде `ci-main` с `cancel-in-progress: false` при 3 быстрых мерджах подряд выбросит средний коммит из очереди ожидания.

```yaml title=".github/workflows/ci.yml"
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- **Изоляция Pull Request:** у каждого PR своя группа по номеру (`CI-12`), новый коммит в PR отменяет только старый незавершённый прогон внутри этого же PR.
- **100% аудит на `main`:** каждый пуш в `main` (и ручной `workflow_dispatch`) получает уникальный `github.run_id` и `cancel-in-progress: false` — ни один коммит в главной ветке не пропускается.

## 5. С `Turborepo` vs без него: граф `--affected`, `fetch-depth` и `TURBO_SCM_BASE`

### Почему в монорепозитории `Turborepo` выигрывает у голого `pnpm -r` и `paths:`

| Подход | Как работает | Скрытые риски и ограничения |
| :--- | :--- | :--- |
| **Обычный проект / `pnpm -r`** | На каждый коммит пересобирает и проверяет все пакеты подряд в лоб. | С ростом числа сервисов время CI растёт линейно; правка одной статьи `.mdx` пересобирает весь бэкенд. |
| **Фильтры `paths:` в GitHub Actions** | Пропускает джобу целиком, если не изменились указанные папки. | Обязательная проверка в Branch Protection зависает в статусе _Waiting_; легко забыть про связь `packages/shared-schemas` → `apps/api`. |
| **`Turborepo --affected` (наш выбор)** | Все джобы стартуют всегда, а `Turborepo` по Git-диффу и графу зависимостей пропускает незатронутые пакеты с кодом `0`. | Требует истории Git (`fetch-depth: '0'`) и явной точки отсчёта (`TURBO_SCM_BASE`) на PR. |

Как ведёт себя `--affected` на Pull Request:
- **Правки только в `apps/api/**`:** проверяется и собирается **исключительно `@repo/api`**; `@repo/web` и `@repo/ui` пропускаются за ~1 секунду со статусом `Success`.
- **Правки в `packages/shared-schemas/**`:** Turborepo вычисляет обратных потребителей и проверяет `@repo/shared-schemas`, `@repo/api`, `@repo/telemetry-ms` и `@repo/web`.
- **Правки в `packages/ui/**`:** пересобираются `@repo/ui` (`build-storybook`) и `@repo/web`, не трогая бэкенд.
- **Корневые конфиги (`tsconfig.base.json`, `pnpm-workspace.yaml`):** включены в `globalDependencies` внутри `turbo.json`, поэтому при их изменении перепроверяется весь монорепозиторий.

> [!IMPORTANT]
> **Два обязательных нюанса GitHub Actions для работы `--affected`:**
> 1. **Строковые `'0' || '1'` в `fetch-depth`:** в выражениях GitHub Actions число `0` считается `falsy`, поэтому конструкция `cond && 0 || 1` всегда вычисляется в `1` (shallow clone без истории). Использование строк `fetch-depth: ${{ github.event_name == 'pull_request' && '0' || '1' }}` гарантирует полноценную историю `0` на PR и быстрый `1` на `main`.
> 2. **`TURBO_SCM_BASE="${{ github.event.pull_request.base.sha }}"`:** на событии `pull_request` экшен `actions/checkout` забирает только merge-коммит `refs/pull/<n>/merge` в detached `HEAD` — на раннере нет ни локальной ветки `main`, ни `origin/main`. Прямая передача хэша базового коммита из контекста PR даёт Turborepo точную точку сравнения без лишних сетевых `git fetch`.

*(На ветке `main` флаг `--affected` намеренно отключён: главная ветка всегда проходит полную проверку, ускоряемую кэшем `.turbo` — при правке `.md`-документации `FULL TURBO` закрывает сборку за пару секунд, а при обновлении `.mdx` внутри `apps/web/content/` пересобирается только `@repo/web`, пока бэкенд берётся из кэша.)*

## 6. Подготовка кодогенерации в `typecheck` и 3 слоя кэширования

### Зачем `typecheck` передаёт `prepare-codegen: "true"`

В `turbo.json` у задачи `typecheck` указано `"dependsOn": ["^typecheck"]` (а не `^build`), чтобы пакеты проверяли типы параллельно, не дожидаясь тяжёлых бандлов. На чистом раннере сразу после `checkout` ещё нет трёх сгенерированных артефактов, на которые ссылается TypeScript:

1. Деклараций `packages/shared-schemas/dist/index.d.ts` (их импортируют `api`, `telemetry-ms` и `web`).
2. Типов моделей БД в `@prisma/client` для `apps/api`.
3. Типов маршрутов Next.js в `.next/types/*`, которые подключает `apps/web/next-env.d.ts`.

Флаг `prepare-codegen: "true"` компилирует эти три слоя до старта `turbo run typecheck`. В джобе `build` он не требуется: там уже работает цепочка `"dependsOn": ["^build"]` (сначала собирается `@repo/shared-schemas`), а скрипт сборки `@repo/api` сам вызывает `prisma generate && tsc -p tsconfig.build.json`.

### Три слоя кэша и защита от Cache Poisoning

1. **Store `pnpm`:** кэшируется в `actions/setup-node@v6` (`cache: pnpm`) во всех джобах установки зависимостей.
2. **Артефакты Turborepo (`.turbo`):** сохраняются и восстанавливаются в `build` по ключу `${{ runner.os }}-turbo-build-${{ github.sha }}` с префиксным фолбеком `${{ runner.os }}-turbo-build-`.
3. **Кэш компилятора Next.js (`apps/web/.next/cache`):** привязан к хэшам `pnpm-lock.yaml` и `apps/web/**`, сохраняя промежуточный кэш webpack/SWC между прогонами.

> [!TIP]
> **Изоляция кэша от отравления (Cache Poisoning):** По правилам GitHub Actions прогоны на Pull Request могут *читать* кэш ветки `main` через `restore-keys`, но **не могут** перезаписывать кэш `main`. При масштабировании команды `.turbo` легко переводится на Vercel Remote Cache через секреты `TURBO_TOKEN` и `TURBO_TEAM` без правки графа джобов.

## 7. Supply-Chain шлюз `security` и план развития CI/CD

### Зачем вынесен отдельный job `security` (и почему без `node_modules`)

```yaml title=".github/workflows/ci.yml"
  security:
    name: Security & Infra Config
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository (shallow)
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Setup pnpm
        uses: pnpm/action-setup@v5

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"

      - name: Validate Docker Compose configuration
        run: docker compose config --quiet

      - name: Audit production dependencies
        run: pnpm audit --prod --audit-level=high
```

- **Защита цепочки поставок (Supply-Chain Security):** многие атаки на npm-пакеты происходят через вредоносные `postinstall`-скрипты во время установки или уязвимости в транзитивных библиотеках. Изолированный job `security` **не устанавливает `node_modules`**, а проверяет уже зафиксированный граф зависимостей напрямую по `pnpm-lock.yaml`.
- **Порядок шагов:** сначала быстрая офлайн-валидация синтаксиса `docker-compose.yml` (`docker compose config --quiet`), затем сетевой аудит `pnpm audit --prod --audit-level=high` — проблема реестра npm не скроет сломанную конфигурацию контейнеров.
- **Почему именно `--prod --audit-level=high`:** инструменты разработки (`Storybook`, `Vite`, `Biome`, `Turbo`) не попадают в финальные runtime-контейнеры `docker/*.Dockerfile` (`pnpm prune --prod`). Проверка только `--prod` держит высокий уровень сигнал/шум без ложных блокировок из-за dev-утилит.
- **Управляемые исключения в `pnpm 12`:** если когда-либо потребуется временно задокументировать недостижимую или ложноположительную уязвимость, используется блок `audit.ignore` в `pnpm-workspace.yaml` (через `pnpm audit --ignore <GHSA>`).

### Дорожная карта расширения CI/CD

1. **`unit-tests` (`Vitest`):** параллельный job в Stage 1 (`needs: []`) с `prepare-codegen: "true"`, `fetch-depth: '0'` / `TURBO_SCM_BASE` на PR и `turbo run test --affected` для проверки Zod-контрактов, `Zustand`-сторов и сервисов NestJS.
2. **`e2e` (`Playwright`):** job после `build` (`needs: [ lint, typecheck, build ]`) с кэшем Chromium, проверкой RBAC-флоу (`GuestPassModal` → `HttpOnly` кука → `<Redact />`) и загрузкой отчётов/трейсов (`actions/upload-artifact`) по `if: failure()`.
3. **Дополнительный hardening:** еженедельный `schedule:` крон для `security` + `.github/dependabot.yml` (чтобы новые CVE ловились даже в недели без коммитов), `persist-credentials: false` на `actions/checkout@v6` и `actionlint` внутри `lint`.
4. **Раздельный CD (Continuous Delivery):** отдельные per-service деплои (`apps/web` на Vercel с Remote Cache; `apps/api` и `apps/telemetry-ms` через `docker/*.Dockerfile` с `turbo prune --docker`), чтобы добавление новых `.mdx`-конспектов не пересобирало Docker-образы бэкенда.
