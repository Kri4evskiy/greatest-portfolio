## 1. Анатомія GitHub Actions: як влаштований наш CI/CD

Увесь конвеєр описаний у `.github/workflows/ci.yml`, спирається на перевикористовуваний **Composite Action** (`.github/actions/setup-workspace/action.yml`) і граф задач `turbo.json`. Базова ідея GitHub Actions: **кожен `job` запускається на окремій чистій віртуальній машині (`ubuntu-latest`)** зі своєю файловою системою та пам’яттю.

### Ключові секції та поля `.github/workflows/ci.yml`

| Поле YAML | Призначення і що робить у нашому проєкті |
| :--- | :--- |
| **`on:`** | Тригери запуску: `push` у `main`, `pull_request` (у цільову гілку `main`) і ручний `workflow_dispatch` (кнопка *Run workflow* в UI GitHub). |
| **`permissions:`** | Видає тимчасовому токену `GITHUB_TOKEN` мінімальні права (принцип Least Privilege): лише `contents: read` (читання коду без права пушу чи зміни релізів). |
| **`concurrency:`** | Керує паралельними запусками одного workflow: скасовує застарілі перевірки всередині одного PR та захищає кожен коміт у `main`. |
| **`env:`** | Змінні середовища на весь workflow (`CI: true`, `LEFTHOOK: 0`, вимкнення телеметрії `DO_NOT_TRACK`, `TURBO_TELEMETRY_DISABLED`, `NEXT_TELEMETRY_DISABLED`). |
| **`jobs.<id>.runs-on:`** | Вибір образу віртуальної машини (`ubuntu-latest`). |
| **`jobs.<id>.needs:`** | Задає порядок (граф залежностей). Наприклад, `needs: [ lint, typecheck ]` не запустить `build`, доки обидва батьки не завершаться успішно. |
| **`name:` / `id:`** | `name:` — людиночитана назва кроку/джоби в UI GitHub; `id:` — технічний ідентифікатор кроку для звернення до його `${{ steps.<id>.outputs.* }}`. |
| **`if:`** | Умова запуску кроку чи джоби (наприклад, `if: inputs.prepare-codegen == 'true'` або `if: failure()` для завантаження звітів). |
| **`steps` (`uses:` vs `run:`)** | `uses:` запускає готовий екшен (із Marketplace або локальної папки `./.github/actions/...`), а `run:` виконує bash-команду на раннері. |
| **`${{ ... }}` контексти** | Динамічні змінні від GitHub: `github.event_name` (`push` чи `pull_request`), `github.sha`, `github.event.pull_request.base.sha`, `runner.os`. |

### `inputs` і `outputs`: як кроки та джоби обмінюються даними

Оскільки в GitHub Actions не можна просто оголосити спільну JS-змінну для всього файлу, для передачі параметрів використовують **інпути (`inputs`)** й **аутпути (`outputs`)**:

1. **Усередині Composite Action (`action.yml`) — параметризація перевикористовуваного блоку:**
   - **`inputs:`** — аргументи, які викликаючий job передає всередину через `with:`. У нас у `setup-workspace` це `prepare-codegen` (`required: false`, `default: "false"`): job `typecheck` передає `"true"`, а інші залишають `"false"`.
   - **`outputs:`** — значення, які крок усередині екшена може повернути назовні (через запис у `$GITHUB_OUTPUT`), щоб використати їх у наступних кроках того ж job.
2. **Між різними `jobs` (на рівні різних VM):**
   - Оскільки кожен job має власну віртуальну машину, передати рядок (наприклад, зібраний тег Docker-образу, URL прев’ю-деплою чи прапор `has-changes`) із `job_a` у `job_b` можна через `jobs.job_a.outputs`:
     1. Усередині `job_a` крок із `id: meta` пише `echo "tag=v1.2.3" >> "$GITHUB_OUTPUT"`.
     2. На рівні `job_a` оголошується `outputs: { tag: ${{ steps.meta.outputs.tag }} }`.
     3. У `job_b` ставиться `needs: [ job_a ]` і значення читається через `${{ needs.job_a.outputs.tag }}`.
   - Для важких файлів (збірки `.next`, скріншоти Playwright) замість `outputs` (вони підходять лише для коротких рядків) застосовують **`actions/upload-artifact`** і **`actions/download-artifact`**.

> [!NOTE]
> **Три рівні перевикористання в GitHub Actions:** поодинокі послідовності кроків оформлюються як **Composite Action** (`uses: ./.github/actions/...`), готові сторонні кроки беруться з Marketplace (`uses: actions/checkout@v6`), а повторювані цілком джоби чи CD-пайплайни виносяться у **Reusable Workflows** (`on: workflow_call`).

## 2. Граф задач (DAG) і чому обрано 5 окремих Jobs

Замість одного довгого скрипту перевірки побудовані як **двоступеневий спрямований ациклічний граф (DAG)**, у який без перероблень додаються майбутні автотести:

```text
Stage 1 (Паралельний Fail-Fast та граф типів)    Stage 2 (Важкі збірки після шлюзів)
─────────────────────────────────────────────    ──────────────────────────────────
[lint] (Biome 2.6, shallow) ─────────────────┐
                                             ├──▶ [build] (Turborepo + .turbo + .next/cache)
[typecheck] (tsc + prepare-codegen) ─────────┤
                                             └──▶ [storybook] (@repo/ui build-storybook)
[security] (Compose + pnpm audit, без install) ─▶ Незалежний supply-chain шлюз

Слоти під розширення (без перебудови DAG):
[unit-tests] (Vitest) ──────────────────────────▶ Паралельно Stage 1 (поруч із lint / typecheck)
[e2e] (Playwright + Chromium) ──────────────────▶ Stage 2/3 з needs: [ lint, typecheck, build ]
```

### Профілі всіх 5 Jobs

| Job | Залежності (`needs`) | Git `fetch-depth` | Ставить `node_modules`? | Команда (`pull_request` vs `main`) |
| :--- | :--- | :--- | :--- | :--- |
| **`lint`** | — | `'1'` (shallow) | Так (без кодогенерації) | `pnpm run lint` (`biome check .` по всьому репозиторію за ~150 мс) |
| **`security`** | — | `'1'` (shallow) | **Ні** | `docker compose config --quiet` → `pnpm audit --prod --audit-level=high` |
| **`typecheck`** | — | PR: `'0'`, `main`: `'1'` | Так + `prepare-codegen` | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run typecheck` |
| **`build`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Так | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run build` |
| **`storybook`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Так | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `turbo run build-storybook` |

### Чому Multi-Job DAG кращий за один монолітний Job

Об’єднання всіх команд в один job економить ~15–30 секунд на старті віртуальних машин (`checkout` + `setup-workspace`), але ми **свідомо обрали** модульний граф:

1. **Готові слоти під `Vitest` та `Playwright` E2E:** швидкі unit-тести стають у Stage 1 паралельно з `typecheck`, а важчий браузерний `Playwright` підключається після `build` зі своїм кешем Chromium і БД, не сповільнюючи `lint`, `security` та `storybook`.
2. **Миттєвий Fail-Fast та економія збірок:** у PR Checks одразу видно, який контур упав (`Lint`, `Security`, `Typecheck`, `Build` або `Storybook`), а `needs: [ lint, typecheck ]` фізично не дає запускати збірки Next.js і Storybook при зламаному форматуванні чи типах.
3. **Розділення прав та ізоляція `node_modules`:** `security` взагалі не встановлює `node_modules` і не виконує install-скрипти пакетів, а `lint` і `security` завантажують лише останній коміт (`fetch-depth: 1`).
4. **Атомарні обов’язкові перевірки (Branch Protection):** кожен job виступає окремим Required Status Check перед злиттям у `main`.
5. **Незалежний сигнал щодо безпеки:** `security` не блокує `build` та `storybook` — при появі нового CVE у сторонній бібліотеці розробник усе одно бачить, чи збирається код.

## 3. DRY-ініціалізація воркспейсу (`.github/actions/setup-workspace/action.yml`)

Щоб не дублювати налаштування `pnpm`, `Node.js 22` та кешу стору в 4+ джобах, уся підготовка винесена в локальний Composite Action:

```yaml title=".github/actions/setup-workspace/action.yml"
inputs:
  prepare-codegen:
    description: Build @repo/shared-schemas and generate Prisma Client before typecheck
    required: false
    default: "false"

runs:
  using: composite
  steps:
    - name: Setup pnpm
      uses: pnpm/action-setup@v5

    - name: Setup Node.js
      uses: actions/setup-node@v6
      with:
        node-version: "22"
        cache: pnpm

    - name: Install dependencies
      shell: bash
      run: pnpm install --frozen-lockfile

    - name: Prepare generated types (@repo/shared-schemas, Prisma Client & Next.js routes)
      if: inputs.prepare-codegen == 'true'
      shell: bash
      run: |
        pnpm --filter @repo/shared-schemas build
        pnpm --filter @repo/api prisma:generate
        pnpm --filter @repo/web exec next typegen
```

Ключові деталі реалізації:

- **Порядок `pnpm/action-setup@v5` до `actions/setup-node@v6`:** опція `cache: pnpm` потребує вже наявного бінарника `pnpm`, щоб визначити шлях до стору. Версія не дублюється в YAML — екшен читає `"packageManager": "pnpm@12.18.0"` із кореневого `package.json`.
- **Єдиний runtime для Actions:** `actions/checkout@v6`, `actions/setup-node@v6`, `actions/cache@v5` і `pnpm/action-setup@v5` працюють на сучасному Node 24 runtime.
- **`pnpm install --frozen-lockfile` із білим списком `allowBuilds`:** на відміну від продакшен-Dockerfiles (`--ignore-scripts`), у CI дозволеним пакетам (`@prisma/client`, `@swc/core`, `@biomejs/biome`) потрібно скомпілювати бінарники. Безпеку забезпечує `allowBuilds` у `pnpm-workspace.yaml` — будь-які сторонні `postinstall`-скрипти заблоковані за замовчуванням.
- **`LEFTHOOK: 0` та вимкнення телеметрії:** глобальна `LEFTHOOK: 0` вимикає встановлення локальних git-хуків скриптом `prepare` усередині ефемерного раннера.

## 4. `concurrency` без втрати комітів у гілці `main`

Тонкість рушія GitHub Actions: в одній `concurrency`-групі зберігається максимум **1 активний + 1 очікуючий** прогон. Статична група на кшталт `ci-main` із `cancel-in-progress: false` при 3 швидких мерджах поспіль витіснить середній коміт із черги очікування.

```yaml title=".github/workflows/ci.yml"
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- **Ізоляція Pull Request:** кожен PR має власну групу за номером (`CI-12`), новий коміт у PR скасовує лише старий незавершений прогон усередині цього ж PR.
- **100% аудит на `main`:** кожен пуш у `main` (і ручний `workflow_dispatch`) отримує унікальний `github.run_id` і `cancel-in-progress: false` — жоден коміт у головній гілці не пропускається.

## 5. З `Turborepo` vs без нього: граф `--affected`, `fetch-depth` та `TURBO_SCM_BASE`

### Чому в монорепозиторії `Turborepo` виграє у голого `pnpm -r` та `paths:`

| Підхід | Як працює | Приховані ризики та обмеження |
| :--- | :--- | :--- |
| **Звичайний проєкт / `pnpm -r`** | На кожен коміт перезбирає та перевіряє всі пакети підряд в лоб. | Зі зростанням числа сервісів час CI росте лінійно; правка однієї статті `.mdx` перезбирає весь бекенд. |
| **Фільтри `paths:` у GitHub Actions** | Пропускає джобу цілком, якщо не змінились зазначені папки. | Обов’язкова перевірка в Branch Protection зависає у статусі _Waiting_; легко пропустити зв’язок `packages/shared-schemas` → `apps/api`. |
| **`Turborepo --affected` (наш вибір)** | Усі джоби стартують завжди, а `Turborepo` за Git-дифом і графом залежностей пропускає незатронуті пакети з кодом `0`. | Потребує історії Git (`fetch-depth: '0'`) та явної точки відліку (`TURBO_SCM_BASE`) на PR. |

Як поводиться `--affected` на Pull Request:
- **Зміни лише в `apps/api/**`:** перевіряється і збирається **виключно `@repo/api`**; `@repo/web` і `@repo/ui` пропускаються за ~1 секунду зі статусом `Success`.
- **Зміни в `packages/shared-schemas/**`:** Turborepo обчислює споживачів і перевіряє `@repo/shared-schemas`, `@repo/api`, `@repo/telemetry-ms` та `@repo/web`.
- **Зміни в `packages/ui/**`:** перезбираються `@repo/ui` (`build-storybook`) і `@repo/web`, не чіпаючи бекенд.
- **Кореневі конфіги (`tsconfig.base.json`, `pnpm-workspace.yaml`):** оголошені в `globalDependencies` усередині `turbo.json`, тому при їх редагуванні перевіряється весь монорепозиторій.

> [!IMPORTANT]
> **Два обов’язкові нюанси GitHub Actions для `--affected`:**
> 1. **Рядкові `'0' || '1'` у `fetch-depth`:** у виразах GitHub Actions число `0` вважається `falsy`, тому конструкція `cond && 0 || 1` завжди обчислюється як `1` (shallow clone без історії). Використання рядків `fetch-depth: ${{ github.event_name == 'pull_request' && '0' || '1' }}` гарантує повну історію `0` на PR і швидкий `1` на `main`.
> 2. **`TURBO_SCM_BASE="${{ github.event.pull_request.base.sha }}"`:** на події `pull_request` екшен `actions/checkout` забирає лише merge-коміт `refs/pull/<n>/merge` у detached `HEAD` — на раннері немає ні локальної гілки `main`, ні `origin/main`. Пряма передача хешу базового коміту з контексту PR дає Turborepo точну точку порівняння без зайвих мережевих `git fetch`.

*(На гілці `main` прапор `--affected` навмисно вимкнено: головна гілка завжди проходить повну перевірку, прискорену кешем `.turbo` — при редагуванні `.md`-документації `FULL TURBO` закриває збірку за пару секунд, а при правці `.mdx` усередині `apps/web/content/` перезбирається лише `@repo/web`, тоді як бекенд береться з кешу.)*

## 6. Підготовка кодогенерації в `typecheck` і 3 шари кешування

### Навіщо `typecheck` передає `prepare-codegen: "true"`

У `turbo.json` задача `typecheck` має `"dependsOn": ["^typecheck"]` (а не `^build`), щоб пакети перевіряли типи паралельно, не чекаючи важких бандлів. На порожньому раннері одразу після `checkout` ще немає трьох згенерованих артефактів, на які посилається TypeScript:

1. Декларацій `packages/shared-schemas/dist/index.d.ts` (їх імпортують `api`, `telemetry-ms` і `web`).
2. Типів моделей БД у `@prisma/client` для `apps/api`.
3. Типів маршрутів Next.js у `.next/types/*`, які підключає `apps/web/next-env.d.ts`.

Прапор `prepare-codegen: "true"` компілює ці три шари до старту `turbo run typecheck`. У джобі `build` він не потрібен: там уже працює ланцюжок `"dependsOn": ["^build"]` (спочатку збирається `@repo/shared-schemas`), а скрипт збірки `@repo/api` сам викликає `prisma generate && tsc -p tsconfig.build.json`.

### Три шари кешу та захист від Cache Poisoning

1. **Store `pnpm`:** кешується в `actions/setup-node@v6` (`cache: pnpm`) в усіх джобах зі встановленням залежностей.
2. **Артефакти Turborepo (`.turbo`):** зберігаються та відновлюються в `build` за ключем `${{ runner.os }}-turbo-build-${{ github.sha }}` із префіксним фолбеком `${{ runner.os }}-turbo-build-`.
3. **Кеш компілятора Next.js (`apps/web/.next/cache`):** прив’язаний до хешів `pnpm-lock.yaml` і `apps/web/**`, зберігаючи проміжний кеш webpack/SWC між прогонами.

> [!TIP]
> **Ізоляція кешу від отруєння (Cache Poisoning):** За правилами GitHub Actions прогони на Pull Request можуть *читати* кеш гілки `main` через `restore-keys`, але **не можуть** перезаписувати кеш `main`. При масштабуванні команди `.turbo` легко перевести на Vercel Remote Cache через секрети `TURBO_TOKEN` і `TURBO_TEAM` без правки графа джобів.

## 7. Supply-Chain шлюз `security` та дорожня карта розвитку CI/CD

### Навіщо винесений окремий job `security` (і чому без `node_modules`)

```yaml title=".github/workflows/ci.yml"
  security:
    name: Security & Infra Config
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository (shallow)
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Setup pnpm
        uses: pnpm/action-setup@v5

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"

      - name: Validate Docker Compose configuration
        run: docker compose config --quiet

      - name: Audit production dependencies
        run: pnpm audit --prod --audit-level=high
```

- **Захист ланцюга постачання (Supply-Chain Security):** чимало атак на npm-пакети відбуваються через шкідливі `postinstall`-скрипти під час встановлення або вразливості в транзитивних бібліотеках. Ізольований job `security` **не встановлює `node_modules`**, а перевіряє вже зафіксований граф залежностей напряму по `pnpm-lock.yaml`.
- **Порядок кроків:** спершу швидка офлайн-валідація синтаксису `docker-compose.yml` (`docker compose config --quiet`), далі мережевий аудит `pnpm audit --prod --audit-level=high` — проблема реєстру npm не приховає зламану конфігурацію контейнерів.
- **Чому саме `--prod --audit-level=high`:** інструменти розробки (`Storybook`, `Vite`, `Biome`, `Turbo`) не потрапляють у фінальні runtime-контейнери `docker/*.Dockerfile` (`pnpm prune --prod`). Перевірка лише `--prod` тримає високий рівень сигнал/шум без хибних блокувань через dev-утиліти.
- **Керовані винятки у `pnpm 12`:** якщо колись знадобиться тимчасово задокументувати недосяжну чи хибнопозитивну вразливість, використовується блок `audit.ignore` у `pnpm-workspace.yaml` (через `pnpm audit --ignore <GHSA>`).

### Дорожня карта розширення CI/CD

1. **`unit-tests` (`Vitest`):** паралельний job у Stage 1 (`needs: []`) із `prepare-codegen: "true"`, `fetch-depth: '0'` / `TURBO_SCM_BASE` на PR та `turbo run test --affected` для перевірки Zod-контрактів, `Zustand`-сторів і сервісів NestJS.
2. **`e2e` (`Playwright`):** job після `build` (`needs: [ lint, typecheck, build ]`) із кешем Chromium, перевіркою RBAC-флоу (`GuestPassModal` → `HttpOnly` кука → `<Redact />`) та завантаженням звітів/трейсів (`actions/upload-artifact`) по `if: failure()`.
3. **Додатковий hardening:** щотижневий `schedule:` крон для `security` + `.github/dependabot.yml` (щоб нові CVE виявлялися навіть у тижні без комітів), `persist-credentials: false` на `actions/checkout@v6` та `actionlint` усередині `lint`.
4. **Роздільний CD (Continuous Delivery):** окремі per-service деплої (`apps/web` на Vercel із Remote Cache; `apps/api` і `apps/telemetry-ms` через `docker/*.Dockerfile` із `turbo prune --docker`), щоб додавання нових `.mdx`-конспектів не перезбирало Docker-образи бекенду.
