## 1. Архітектура нашої 3-рівневої піраміди тестування

Замість повільних E2E-тестів для перевірки чистої логіки чи надмірного мокування фреймворку кожен шар монорепозиторію тестується найлегшим інструментом, що зберігає реальну семантику виконання: загалом **65 unit/integration тестів Vitest у 4 пакетах**, повноцінний **HTTP E2E-контур на Supertest** проти NestJS `AppModule` та **Playwright Chromium POM E2E**:

```text
                        ▲
                       / \
                      /   \    Рівень 3: Playwright POM E2E (apps/web/e2e/)
                     / E2E \   Реальний Chromium + зібраний Next.js 16 + NestJS 12 webServer
                    /-------\
                   /  HTTP   \ Рівень 2: NestJS AppModule + Supertest і RTL + MSW v3
                  /  і UI Int \ Реальні DI/CSRF/Guards/Pipes/Filters та TanStack Query + MSW v3
                 /-------------\
                /   Unit і Zod  \ Рівень 1: Ізольований Vitest (65 unit/int тестів у 4 пакетах)
               /_________________\ shared-schemas, web, api, telemetry-ms
```

| Шар | Раннер і бібліотеки | Область і шлях | Що гарантує |
| :--- | :--- | :--- | :--- |
| **Контракти (`Tier 1`)** | `Vitest` (Node) | `packages/shared-schemas/src/__tests__/` | `resolveEndpoint`, межі Zod-схем (`offset <= 500`, `nextOffset`), цілісність усіх 16 локалізованих ADR |
| **Web Unit (`Tier 1`)** | `Vitest` (`node` + `jsdom`) | `apps/web/src/shared/**/__tests__/` | `Axios`, fail-closed Edge Web Crypto `verifyEdgeJwtHs256`, `QueryClient`, гібридні `APP_ROUTES`, `useUIStore` |
| **Web Integration (`Tier 2`)** | `Vitest` + `RTL` + `MSW v3` | `apps/web/src/features/**/__tests__/` | Пагінація, фільтри категорій і сортування через реальний `TanStack Query` |
| **API Unit (`Tier 1`)** | `Vitest` + `unplugin-swc` | `apps/api/src/**/__tests__/*.spec.ts` | `app.config` (`TRUST_PROXY_HOPS`, прод-секрети), захист від CRLF `request-id`, обмежений `PrismaService` fallback, `AuthService` / `JwtRolesGuard` / SSE-ліміти `TelemetryService` |
| **Telemetry Unit (`Tier 1`)** | `Vitest` (Node + `@vitest/coverage-v8`) | `apps/telemetry-ms/src/__tests__/` | `TelemetryMicroserviceController`: Zod-фільтрація, буфер на 50 подій, loopback `127.0.0.1:4001` у `telemetry-ms.config` та `getStats()` |
| **API HTTP E2E (`Tier 2`)** | `Vitest` + `Supertest` | `apps/api/test/auth-and-observability.e2e-spec.ts` | Повний `AppModule`: `/api/capabilities`, публічні метрики, RBAC `403`, CSRF `415`/`403`, хибний `adminPasscode` `403`, `HttpOnly` кука та `X-Request-Id`, невідомий слаг `404`, дедуплікація `helpful`, `ADMIN` `/api/telemetry/admin-diagnostics`, offset (`offset=501` ➔ `400`) і cursor (`cursor=null` ➔ `400`) |
| **Browser E2E (`Tier 3`)** | `Playwright` Chromium | `apps/web/e2e/{fixtures,pages,specs}/` | Публічний доступ до `this-project`, Edge-редирект `src/proxy.ts`, розблокування `GuestPassModal`, пагінація `/system-status` |

### Хто за що відповідає: відмінності між `Vitest`, `SWC`, `MSW v3`, `Supertest` і `Playwright`

Найзручніше уявляти тестову систему як конвеєр, де кожен інструмент виконує суворо одну задачу й не підміняє інші:

1. **`Vitest` (тест-раннер і рушій перевірок):**
   Знаходить тестові файли, надає `describe / it / expect`, ізолює воркери та збирає звіти покриття V8. Сам по собі він не компілює метадані NestJS, не перехоплює HTTP-запити й не відкриває браузер.
2. **`SWC` (`@swc/core` + `unplugin-swc` — Rust-компілятор для NestJS-тестів):**
   Це не тестовий фреймворк, а швидкий компілятор `TypeScript ➔ JavaScript`. Стандартний транспілятор усередині Vite вирізає метадані декораторів (`emitDecoratorMetadata`), через що NestJS ламається під час впровадження залежностей (DI). `SWC` зберігає ці метадані на швидкості Rust, дозволяючи запускати реальні NestJS-модулі всередині `Vitest`.
3. **`MSW v3` (Mock Service Worker — мережевий перехоплювач для фронтенду):**
   Використовується в інтеграційних тестах `apps/web` (`React 19` + `TanStack Query` + `Axios`). Компонент чесно надсилає справжній HTTP-запит на `/api/knowledge/metrics/paginated`, а `MSW` перехоплює його на межі мережі в пам’яті та повертає заздалегідь підготовлений JSON. Це дозволяє перевірити реальну пагінацію, фільтри, ретраї й кешування UI без запущеного бекенду.
4. **`Supertest` (in-memory HTTP-клієнт для бекенду):**
   Використовується в `apps/api/test/auth-and-observability.e2e-spec.ts`. Піднімає реальний `AppModule` NestJS у пам’яті (`DATABASE_URL=""`, `WORKFOLIO_DEMO_MODE="true"`) і надсилає справжні HTTP-запити (`GET /api/capabilities`, `POST /api/auth/guest-pass`, `GET /api/telemetry/admin-diagnostics` тощо), перевіряючи статус-коди, `Set-Cookie`, `CsrfOriginMiddleware`, `ZodValidationPipe`, `JwtRolesGuard` і `SentryExceptionFilter` — без запуску браузера та фронтенду.
5. **`Playwright` (справжній браузер Chromium):**
   Запускає зібрані production-сервери Next.js та NestJS і проходить користувацькі сценарії повністю: від гібридної маршрутизації БЗ і редиректів Edge Proxy до `HttpOnly`-кук, рендеру `.mdx` і пагінації `/system-status`.

> [!NOTE]
> **Роль `Storybook 10` (`@repo/ui`) vs `Vitest` / `Playwright`:** UI-примітиви ізольовані в `packages/ui/` і візуально перевіряються у Storybook без прив’язки до бізнес-API. Мережеві сценарії, кешування, RBAC-редиректи та гідрація живуть у `Vitest` + `Playwright`.

## 2. Чому `Vitest` + `unplugin-swc` замінили `Jest` та `ts-jest`

Наш монорепозиторій працює на **`TypeScript 7` + нативному `ESM` (`"type": "module"`)**, де класичний стек `Jest` стикається з двома системними обмеженнями:

1. **Прив’язка `ts-jest` до старого компілятора:** `ts-jest` зав’язаний на legacy JS API компілятора (`typescript <7`) і потребує крихких експериментальних прапорців VM для нативного ESM.
2. **Метадані декораторів NestJS (`emitDecoratorMetadata`) у ESM:** вбудований у Vite транспілятор (`esbuild` / `oxc`) вирізає `design:paramtypes`, без яких ламається Dependency Injection NestJS (`JwtService`, `PrismaService`, `TelemetryService`). Підключення **`unplugin-swc`** в `apps/api/vitest.base.ts` зберігає метадані декораторів зі швидкістю Rust.

```ts title="apps/api/vitest.base.ts"
function resolveTsExtensionPlugin(): Plugin {
  return {
    name: 'resolve-ts-extension',
    enforce: 'pre',
    async resolveId(source, importer, options) {
      if (!importer || !source.startsWith('.')) {
        return null
      }

      const resolved = await this.resolve(source, importer, {
        ...options,
        skipSelf: true,
      })

      if (resolved && !resolved.external && resolved.id.endsWith('.js')) {
        const tsPath = resolved.id.replace(/\.js$/, '.ts')
        if (existsSync(tsPath)) {
          return tsPath
        }
      }

      return null
    },
  }
}

function ensureSwcNativeCacheDir(): void {
  if (process.env.SWC_NATIVE_BINDING_CACHE) {
    return
  }
  const cacheDir = resolve(import.meta.dirname, '../../.turbo/swc')
  mkdirSync(cacheDir, { recursive: true })
  process.env.SWC_NATIVE_BINDING_CACHE = cacheDir
}
```

### Три обов’язкові нюанси Vitest для NestJS 12

1. **Резолвер розширень `.js` ➔ `.ts`:** за `moduleResolution: "NodeNext"` TypeScript-файли імпортують локальні модулі як `./auth.service.js`. `resolveTsExtensionPlugin()` делегує розв’язання в `this.resolve(..., { skipSelf: true })` і підміняє локальні `.js`-шляхи на існуючі `.ts`-сирці на льоту.
2. **`reflect-metadata` і `pool: 'forks'`:** `apps/api/vitest.setup.ts` одноразово завантажує `reflect-metadata`, а **`pool: 'forks'`** запускає тести в ізольованих процесах замість `worker_threads`, запобігаючи збоям нативної реєстрації `@swc/core`.
3. **`SWC_NATIVE_BINDING_CACHE` + `passThroughEnv`:** `createApiVitestConfig(include)` викликає `ensureSwcNativeCacheDir()` **до** динамічного `import('unplugin-swc')`, спрямовуючи кеш `@swc/core` у короткий шлях `../../.turbo/swc` (менший за Windows `MAX_PATH`). Оголошення `"passThroughEnv": ["SWC_NATIVE_BINDING_CACHE"]` у `turbo.json` не дає Turborepo Strict Env Mode вирізати змінну кешу.

## 3. Патерни фронтенд-тестів: React 19, `TanStack Query` і `MSW v3`

Тестування сучасного Next.js App Router та React 19 вимагає акуратної роботи з асинхронними таймерами, DOM-очищенням і браузерними API:

- **Явні імпорти з `'vitest'` + `afterEach(cleanup)`:** без глобальних `describe`/`it`/`expect` (`globals: false`) строгий TypeScript і Biome не потребують глобальної магії. Проте `@testing-library/react` викликає автоочищення DOM лише за наявності глобального `afterEach`, тому `apps/web/vitest.setup.ts` явно реєструє `afterEach(() => cleanup())`, виключаючи «витік» DOM-вузлів між тестами.
- **Суворий перехопник мережі в `MSW v3`:** інтеграційні тести миттєво падають на будь-якому незамоканому запиті до `/api/*`, викликають `server.resetHandlers()` в `afterEach` і `server.close()` в `afterAll`.
- **Детерміноване скасування запитів при `unmount()`:** перевірка придушення `AbortError` у `makeQueryClient()` монтує `useQuery` із незавершеним `Promise` і викликає `unmount()` без нестабільних `setTimeout`.
- **Захист `window.indexedDB` у `QueryProvider`:** явна перевірка `typeof window.indexedDB !== 'undefined'` перед створенням персистера робить компонент стабільним і в SSR, і в `jsdom`-тестах.
- **Radix UI Portals у RTL:** випадаючі списки `<Select>` та діалоги `<Dialog>` рендеряться через портал напряму в `document.body`, тому запити виконуються через `screen` + `@testing-library/user-event`.

## 4. Playwright E2E: `POM`, 5 кроків `test.step`, `Zero-Cruft data-testid` і масштабований `WebServer`

E2E-сценарії в `apps/web/e2e/` організовані за патерном **Page Object Model (POM)**:

```text
apps/web/e2e/
├── fixtures/app.fixture.ts            # Типізовані фікстури GuestPassPage і SystemStatusPage
├── pages/
│   ├── guest-pass.page.ts             # Інкапсулює модалку, введення імені/ролі та сабміт форми
│   └── system-status.page.ts          # Інкапсулює матрицю capabilities, пагінацію 2-ї сторінки, логи
└── specs/
    └── rbac-and-observability.spec.ts # Повний Hybrid KB + RBAC + /system-status сценарій на базі test.step()
```

### Інженерні стандарти E2E-контуру

1. **Політика `Zero-Cruft data-testid`:** Playwright **ніколи** не шукає елементи за перекладеними текстами (`"Увійти"`, `"Next"`) чи крихкими HTML-тегами. Атрибути `data-testid` (`guest-pass-dialog`, `guest-pass-submit-btn`, `leaderboard-table` тощо) додаються **суворо** до реально запитуваних вузлів.
2. **5-крокова телеметрія `test.step(...)` (`rbac-and-observability.spec.ts`):** кожен етап винесено в окремий крок для прозорих HTML-звітів CI та Playwright Trace Viewer:
   1. `1. Verify public /knowledge-base/this-project article loads directly without redirect`
   2. `2. Redirect unauthenticated guest on protected KB article to GuestPassModal via Edge Proxy`
   3. `3. Issue Guest Pass and verify HttpOnly JWT cookie`
   4. `4. Land on protected MDX article and verify server-compiled content`
   5. `5. Verify /system-status Capability Matrix, Cursor Event Log, and Leaderboard Page 1 -> Page 2`
3. **Масштабовані воркери та serial-режим для stateful-сценаріїв:** `playwright.config.ts` задає `fullyParallel: true` (`...(process.env.CI ? { workers: 2 } : {})`), а `test.describe.configure({ mode: 'serial' })` зберігає суворий порядок кроків у stateful-ланцюжку Hybrid KB ➔ auth ➔ event log.
4. **Node 24 Happy Eyeballs DNS і Next.js `webServer` (`NODE_OPTIONS`):** змінна `NODE_OPTIONS: '--dns-result-order=ipv4first --no-network-family-autoselection'` у `webServer.env` запобігає `AggregateError` (`ECONNREFUSED ::1:4000`) при проксіюванні `/api/*` в IPv4-прив’язаний API на Node 24.

## 5. Вкладка Testing в IDE (`vitest.config.ts`) та інтеграція в CI/CD

### Кореневий конфіг проєктів для Testing Explorer

Окремі `vitest.config.ts` усередині пакетів прискорюють `Turborepo --affected`, а кореневий `vitest.config.ts` (`projects: ['packages/*', 'apps/*']`) об’єднує дерево тестів і V8-покриття для IDE Testing Explorer (`vitest.explorer` + `ms-playwright.playwright`). Покриття збирається командою `pnpm run test:coverage`, а інтерактивний інтерфейс Vitest UI піднімається через `pnpm run test:ui`.

### Інтеграція в GitHub Actions CI (`.github/workflows/ci.yml`)

- **Stage 1 (`unit-tests`):** запускається паралельно з `lint`, `security` і `typecheck`, використовуючи `prepare-codegen: "true"`, динамічний `fetch-depth: '0'` із `TURBO_SCM_BASE` на PR (`turbo run test --affected` для 65 unit/integration тестів Vitest у 4 пакетах), після чого проганяє `pnpm --filter @repo/api test:e2e` (Supertest HTTP E2E).
- **Stage 2 (`e2e`):** стартує після `needs: [ lint, typecheck, build ]`, відновлює кеш `.turbo`, читає точну встановлену версію `@playwright/test` (`id: playwright-version` із `./apps/web/node_modules/@playwright/test/package.json`) і кешує `~/.cache/ms-playwright` за ключем `${{ runner.os }}-playwright-${{ steps.playwright-version.outputs.version }}`. При cache miss виконується `playwright install --with-deps chromium`, при cache hit — лише системні залежності через `playwright install-deps chromium`, далі запускається `pnpm --filter @repo/web test:e2e`, а HTML-звіти та трейси завантажуються через `actions/upload-artifact@v7` суворо при `if: failure()`.
