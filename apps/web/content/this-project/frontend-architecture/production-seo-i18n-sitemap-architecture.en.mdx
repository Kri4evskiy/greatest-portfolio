## 1. The 3-Tier Locale Matrix (`Internal Code` vs `URL Prefix` vs `Hreflang / OpenGraph`)

A core nuance of multilingual SEO in this monorepo is that internal locale codes, public browser URL prefixes, and search engine / social messenger specifications follow different standards.

In `apps/web/src/shared/i18n/routing.ts`, routing uses `localePrefix: { mode: 'as-needed', prefixes: { uk: '/ua' } }`. To prevent inconsistencies across pages, `apps/web/src/shared/lib/seo.ts` explicitly maps each representation:

| Language | Internal Type (`SupportedLocale` & `.mdx` suffix) | Public URL Prefix (`as-needed`) | Search Engine ISO 639-1 (`<html lang>` & `hreflang`) | Messenger Standard (`og:locale`) |
| :--- | :--- | :--- | :--- | :--- |
| **English (Default)** | `'en'` (`*.en.mdx`) | No prefix (`/`, `/cv`, `/knowledge-base`) | `en` (+ `x-default`) | `en_US` |
| **Ukrainian** | `'uk'` (`*.uk.mdx`) | `/ua` (`/ua`, `/ua/cv`, `/ua/knowledge-base`) | `uk` | `uk_UA` |
| **Russian** | `'ru'` (`*.ru.mdx`) | `/ru` (`/ru`, `/ru/cv`, `/ru/knowledge-base`) | `ru` | `ru_RU` |

> [!IMPORTANT]
> According to Google Search Central guidelines, the `hreflang` attribute must use the **ISO 639-1** language code (`uk` for Ukrainian, not the country code `ua`), while its `href` attribute must resolve to the actual public URL (`https://domain.com/ua/...`). Therefore, `buildLanguageAlternatesMap()` maps the `uk` key directly to the `/ua` URL prefix.

## 2. Unified SEO Core & Origin Hardening (`apps/web/src/shared/lib/seo.ts`)

All SEO URL builders live in pure server functions with zero external dependencies:

```typescript title="apps/web/src/shared/lib/seo.ts"
const DEFAULT_SITE_URL = 'http://localhost:3000'

const LOCALE_URL_PREFIX_MAP: Record<SupportedLocale, string> = {
  en: '',
  uk: '/ua',
  ru: '/ru',
}

const OG_LOCALE_MAP: Record<SupportedLocale, string> = {
  en: 'en_US',
  uk: 'uk_UA',
  ru: 'ru_RU',
}

export function resolveSiteUrl(): string {
  const raw = process.env.NEXT_PUBLIC_SITE_URL?.trim()
  if (!raw) return DEFAULT_SITE_URL

  try {
    const parsed = new URL(raw)
    if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:') {
      return DEFAULT_SITE_URL
    }
    return parsed.origin
  } catch {
    return DEFAULT_SITE_URL
  }
}
```

### Why `resolveSiteUrl()` validates `parsed.origin` via `new URL(raw)`
In `apps/web/src/app/[locale]/layout.tsx`, Next.js expects a valid URL instance in `metadataBase: new URL(resolveSiteUrl())`. If a deployment environment accidentally provides a malformed `NEXT_PUBLIC_SITE_URL` (missing protocol or containing trailing path segments), unguarded `new URL()` calls would crash `next build`. Extracting `parsed.origin` with protocol verification (`http:` / `https:`) guarantees a clean origin or a safe fallback to `http://localhost:3000`.

## 3. How `canonical`, `alternates.languages` (`hreflang`), and `openGraph` Work

The `buildPageAlternates(pathname, locale)` helper is used inside `generateMetadata()` across all route levels (`[locale]/layout.tsx`, `[locale]/cv/page.tsx`, `[locale]/knowledge-base/page.tsx`, and `[locale]/knowledge-base/[...slug]/page.tsx`):

```typescript title="apps/web/src/shared/lib/seo.ts"
export function buildLanguageAlternatesMap(pathname: string): Record<string, string> {
  return {
    en: buildLocalizedUrl(pathname, 'en'),
    uk: buildLocalizedUrl(pathname, 'uk'),
    ru: buildLocalizedUrl(pathname, 'ru'),
    'x-default': buildLocalizedUrl(pathname, DEFAULT_LOCALE),
  }
}

export function buildPageAlternates(pathname: string, locale: SupportedLocale = DEFAULT_LOCALE) {
  return {
    canonical: buildLocalizedUrl(pathname, locale),
    languages: buildLanguageAlternatesMap(pathname),
  }
}
```

For `/ru/cv`, Next.js 16 emits the following tags in `<head>`:
1. **`<link rel="canonical" href="https://.../ru/cv" />`** — declares the authoritative URL for the current locale (preventing duplicate indexing from query parameters like `?unlock=knowledge-base`).
2. **`<link rel="alternate" hreflang="en" href="https://.../cv" />`** — links the unprefixed English route.
3. **`<link rel="alternate" hreflang="uk" href="https://.../ua/cv" />`** — links the `/ua`-prefixed Ukrainian route.
4. **`<link rel="alternate" hreflang="ru" href="https://.../ru/cv" />`** — links the `/ru`-prefixed Russian route.
5. **`<link rel="alternate" hreflang="x-default" href="https://.../cv" />`** — defines the default English fallback for unmatched browser locales.
6. **OpenGraph (`og:title`, `og:description`, `og:url`, `og:locale`, `og:type`)** — renders localized Rich Link Previews when shared in **Telegram, LinkedIn, Slack, or Discord** (with `og:type="article"`, `article:published_time`, and `article:tag` added automatically on Knowledge Base notes).

## 4. Static `robots.ts` & `sitemap.ts` and Edge Security Coexistence

Both metadata routes in `apps/web/src/app/` declare `export const dynamic = 'force-static'`, compiling at build time with `0 KB` of client-side JavaScript:

1. **Zero-Friction Edge Proxy Bypass (`src/proxy.ts`):**
   Our Edge Proxy defines:
   ```typescript
   matcher: ['/((?!api|search-index|_next|_vercel|.*\\..*).*)']
   ```
   Any path containing a file extension (`.*\\..*`), including `/robots.txt` and `/sitemap.xml`, bypasses the Edge middleware completely without triggering Web Crypto JWT verification or locale redirects.
2. **Internal Endpoint Isolation in `robots.ts`:**
   ```typescript title="apps/web/src/app/robots.ts"
   rules: [
     {
       userAgent: '*',
       allow: '/',
       disallow: ['/api/', '/search-index/'],
     },
   ]
   ```
   We explicitly disallow `/api/` (backend REST/SSE endpoints) and `/search-index/` (raw JSON dumps used by the client-side `Cmd+K` modal) so search engines only index human-readable pages.
3. **Recursive `.mdx` Discovery in `sitemap.ts`:**
   `sitemap.ts` combines top-level routes (`/`, `/cv`, `/knowledge-base`) with all static folder hubs and articles returned by `getAllStaticKnowledgeSlugArrays()`, pairing each article with its `publishedAt` timestamp from `getAllKnowledgeFrontmatters(DEFAULT_LOCALE)` and emitting localized entries for `en`, `uk`, and `ru`.

## 6. Two-Tier Error Boundary Architecture & Localized `404` (`not-found.tsx` + `[...rest]` + `error.tsx`)

In a multilingual Next.js App Router setup rooted under `app/[locale]/*`, a root-level `app/not-found.tsx` renders **outside** `LocaleRootLayout` (stripping `WorkfolioHeader`, the 2D `Mode × Palette` theme switcher, `Cmd+K` search, and the active locale context).

To preserve the complete shell and localization on `404` or runtime failures, we use a two-tier boundary architecture:

1. **Catch-All Unknown Route Interception (`apps/web/src/app/[locale]/[...rest]/page.tsx` ➔ `[locale]/not-found.tsx`):**
   - Any unmatched URL inside a locale (e.g., `/unknown` or `/ru/unknown`) falls through to `[...rest]/page.tsx`, which immediately invokes `notFound()` from `next/navigation`.
   - Triggering `notFound()` inside the `[locale]` segment activates **`apps/web/src/app/[locale]/not-found.tsx`** — a pure **React Server Component (`0 KB` client JS)** powered by `getTranslations('NotFound')`. It renders inside `<main>` within `LocaleRootLayout`, keeping the header, theme, and footer intact while returning a proper HTTP `404` status code to search engine crawlers.
2. **Two-Tier Runtime Error Boundaries (`[locale]/error.tsx` vs `app/global-error.tsx`):**
   - **`apps/web/src/app/[locale]/error.tsx` (`'use client'`):** localized boundary inside `LocaleRootLayout` (`useTranslations('ErrorPage')`). It catches page-level rendering exceptions while keeping the site header and navigation interactive, logs the exception with Sentry graceful degradation, displays `error.digest`, and provides a `reset()` retry trigger.
   - **`apps/web/src/app/global-error.tsx` (`'use client'`):** last-resort root boundary providing its own `<html>` and `<body>` shell (inferring the locale from `window.location.pathname`) in the rare event that `LocaleRootLayout` itself fails.
