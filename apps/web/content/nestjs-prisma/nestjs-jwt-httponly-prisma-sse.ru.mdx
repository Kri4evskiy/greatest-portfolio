## 1. Почему мы запретили `LocalStorage` для JWT-токенов

Хранение `accessToken` в `window.localStorage` или `sessionStorage` делает приложение уязвимым к любой XSS-атаке: сторонний скрипт или скомпрометированный npm-пакет может прочитать токен одной строкой `localStorage.getItem('token')`.

В нашем монорепозитории реализована схема **HttpOnly Cookie + Dual-Layer RBAC**:

1. При сабмите микро-формы `POST /api/auth/guest-pass` бэкенд **NestJS** создает запись `VisitorSession` в PostgreSQL через **Prisma ORM**.
2. Сервер подписывает JWT и выставляет заголовок `Set-Cookie`:
   - `HttpOnly` — JavaScript в браузере физически не видит куку `kb_access_token` в `document.cookie`.
   - `SameSite=Lax` и `Secure` — защита от CSRF и перехвата трафика.
3. **Уровень 1 (Next.js Edge Middleware):** До рендера любой страницы `/knowledge-base/*` проверяет наличие и структуру куки на Edge.
4. **Уровень 2 (NestJS `JwtRolesGuard`):** Проверяет криптографическую подпись JWT и роль (`USER` / `ADMIN`) при запросах к `/api/knowledge/*`.

## 2. Атомарные инкременты в `Prisma ORM` и `Server-Sent Events`

Когда тимлид открывает статью или нажимает кнопку `Helpful`, бэкенд выполняет атомарный `upsert` в PostgreSQL (`Neon.tech`), исключающий состояние гонки (`race condition`):

```typescript
await this.prisma.articleMetrics.upsert({
  where: { slug },
  update: { helpfulCount: { increment: 1 } },
  create: { slug, category, viewsCount: 1, helpfulCount: 1 },
});
```

Сразу после записи `apps/api` отправляет событие по TCP (` порт 4001`) в выделенный микросервис `apps/telemetry-ms`, а подписчики эндпоинта `GET /api/telemetry/stream` (`@Sse`) мгновенно видят обновление в живом индикаторе футера.
