## 1. Архитектура нашей 3-уровневой пирамиды тестирования

Вместо медленных E2E-тестов для проверки чистой логики или чрезмерного мокирования всего фреймворка каждый слой монорепозитория тестируется самым лёгким инструментом, сохраняющим реальную семантику выполнения: всего **65 unit/integration тестов Vitest в 4 пакетах**, полноценный **HTTP E2E-контур на Supertest** против NestJS `AppModule` и **Playwright Chromium POM E2E**:

```text
                        ▲
                       / \
                      /   \    Уровень 3: Playwright POM E2E (apps/web/e2e/)
                     / E2E \   Реальный Chromium + собранный Next.js 16 + NestJS 12 webServer
                    /-------\
                   /  HTTP   \ Уровень 2: NestJS AppModule + Supertest и RTL + MSW v3
                  /  и UI Int \ Реальные DI/CSRF/Guards/Pipes/Filters и TanStack Query + MSW v3
                 /-------------\
                /   Unit и Zod  \ Уровень 1: Изолированный Vitest (65 unit/int тестов в 4 пакетах)
               /_________________\ shared-schemas, web, api, telemetry-ms
```

| Слой | Раннер и библиотеки | Область и путь | Что гарантирует |
| :--- | :--- | :--- | :--- |
| **Контракты (`Tier 1`)** | `Vitest` (Node) | `packages/shared-schemas/src/__tests__/` | `resolveEndpoint`, границы Zod-схем (`offset <= 500`, `nextOffset`), целостность всех 16 локализованных ADR |
| **Web Unit (`Tier 1`)** | `Vitest` (`node` + `jsdom`) | `apps/web/src/shared/**/__tests__/` | `Axios`, fail-closed Edge Web Crypto `verifyEdgeJwtHs256`, `QueryClient`, гибридные `APP_ROUTES`, `useUIStore` |
| **Web Integration (`Tier 2`)** | `Vitest` + `RTL` + `MSW v3` | `apps/web/src/features/**/__tests__/` | Пагинация, фильтры категорий и сортировка через реальный `TanStack Query` |
| **API Unit (`Tier 1`)** | `Vitest` + `unplugin-swc` | `apps/api/src/**/__tests__/*.spec.ts` | `app.config` (`TRUST_PROXY_HOPS`, прод-секреты), защита от CRLF `request-id`, ограниченный `PrismaService` fallback, `AuthService` / `JwtRolesGuard` / SSE-лимиты `TelemetryService` |
| **Telemetry Unit (`Tier 1`)** | `Vitest` (Node + `@vitest/coverage-v8`) | `apps/telemetry-ms/src/__tests__/` | `TelemetryMicroserviceController`: Zod-фильтрация, буфер на 50 событий, loopback `127.0.0.1:4001` в `telemetry-ms.config` и `getStats()` |
| **API HTTP E2E (`Tier 2`)** | `Vitest` + `Supertest` | `apps/api/test/auth-and-observability.e2e-spec.ts` | Полный `AppModule`: `/api/capabilities`, публичные метрики, RBAC `403`, CSRF `415`/`403`, неверный `adminPasscode` `403`, `HttpOnly` кука и `X-Request-Id`, неизвестный слаг `404`, дедупликация `helpful`, `ADMIN` `/api/telemetry/admin-diagnostics`, offset (`offset=501` ➔ `400`) и cursor (`cursor=null` ➔ `400`) |
| **Browser E2E (`Tier 3`)** | `Playwright` Chromium | `apps/web/e2e/{fixtures,pages,specs}/` | Публичный доступ к `this-project`, Edge-редирект `src/proxy.ts`, разблокировка `GuestPassModal`, пагинация `/system-status` |

### Кто за что отвечает: различия между `Vitest`, `SWC`, `MSW v3`, `Supertest` и `Playwright`

Удобнее всего представить тестовую систему как конвейер, где каждый инструмент решает строго одну задачу и не подменяет остальные:

1. **`Vitest` (тест-раннер и движок проверок):**
   Находит тестовые файлы, предоставляет `describe / it / expect`, изолирует воркеры и собирает отчёты покрытия V8. Сам по себе он не компилирует метаданные NestJS, не перехватывает HTTP-запросы и не открывает браузер.
2. **`SWC` (`@swc/core` + `unplugin-swc` — Rust-компилятор для NestJS-тестов):**
   Это не тестовый фреймворк, а быстрый компилятор `TypeScript ➔ JavaScript`. Стандартный транспилятор внутри Vite вырезает метаданные декораторов (`emitDecoratorMetadata`), из-за чего NestJS ломается при внедрении зависимостей (DI). `SWC` сохраняет эти метаданные на скорости Rust, позволяя запускать реальные NestJS-модули внутри `Vitest`.
3. **`MSW v3` (Mock Service Worker — сетевой перехватчик для фронтенда):**
   Используется в интеграционных тестах `apps/web` (`React 19` + `TanStack Query` + `Axios`). Компонент честно отправляет настоящий HTTP-запрос на `/api/knowledge/metrics/paginated`, а `MSW` перехватывает его на границе сети в памяти и возвращает заготовленный JSON. Это позволяет проверить реальную пагинацию, фильтры, ретраи и кэширование UI без поднятого бэкенда.
4. **`Supertest` (in-memory HTTP-клиент для бэкенда):**
   Используется в `apps/api/test/auth-and-observability.e2e-spec.ts`. Поднимает реальный `AppModule` NestJS в памяти (`DATABASE_URL=""`, `WORKFOLIO_DEMO_MODE="true"`) и отправляет настоящие HTTP-запросы (`GET /api/capabilities`, `POST /api/auth/guest-pass`, `GET /api/telemetry/admin-diagnostics` и др.), проверяя статус-коды, `Set-Cookie`, `CsrfOriginMiddleware`, `ZodValidationPipe`, `JwtRolesGuard` и `SentryExceptionFilter` — без запуска браузера и фронтенда.
5. **`Playwright` (настоящий браузер Chromium):**
   Запускает собранные production-серверы Next.js и NestJS и проходит пользовательские сценарии целиком: от гибридной маршрутизации БЗ и редиректов Edge Proxy до `HttpOnly`-кук, рендера `.mdx` и пагинации `/system-status`.

> [!NOTE]
> **Роль `Storybook 10` (`@repo/ui`) vs `Vitest` / `Playwright`:** UI-примитивы изолированы в `packages/ui/` и визуально тестируются в Storybook без привязки к бизнес-API. Сетевые сценарии, кэширование, RBAC-редиректы и гидрация живут в `Vitest` + `Playwright`.

## 2. Почему `Vitest` + `unplugin-swc` заменили `Jest` и `ts-jest`

Наш монорепозиторий работает на **`TypeScript 7` + нативном `ESM` (`"type": "module"`)**, где классический стек `Jest` сталкивается с двумя системными ограничениями:

1. **Привязка `ts-jest` к старому компилятору:** `ts-jest` завязан на legacy JS API компилятора (`typescript <7`) и требует хрупких экспериментальных флагов VM для нативного ESM.
2. **Метаданные декораторов NestJS (`emitDecoratorMetadata`) в ESM:** встроенный в Vite транспилятор (`esbuild` / `oxc`) вырезает `design:paramtypes`, без которых ломается Dependency Injection NestJS (`JwtService`, `PrismaService`, `TelemetryService`). Подключение **`unplugin-swc`** в `apps/api/vitest.base.ts` сохраняет метаданные декораторов на скорости Rust.

```ts title="apps/api/vitest.base.ts"
function resolveTsExtensionPlugin(): Plugin {
  return {
    name: 'resolve-ts-extension',
    enforce: 'pre',
    async resolveId(source, importer, options) {
      if (!importer || !source.startsWith('.')) {
        return null
      }

      const resolved = await this.resolve(source, importer, {
        ...options,
        skipSelf: true,
      })

      if (resolved && !resolved.external && resolved.id.endsWith('.js')) {
        const tsPath = resolved.id.replace(/\.js$/, '.ts')
        if (existsSync(tsPath)) {
          return tsPath
        }
      }

      return null
    },
  }
}

function ensureSwcNativeCacheDir(): void {
  if (process.env.SWC_NATIVE_BINDING_CACHE) {
    return
  }
  const cacheDir = resolve(import.meta.dirname, '../../.turbo/swc')
  mkdirSync(cacheDir, { recursive: true })
  process.env.SWC_NATIVE_BINDING_CACHE = cacheDir
}
```

### Три обязательные тонкости Vitest для NestJS 12

1. **Резолвер расширений `.js` ➔ `.ts`:** при `moduleResolution: "NodeNext"` TypeScript-файлы импортируют локальные модули как `./auth.service.js`. `resolveTsExtensionPlugin()` делегирует разрешение в `this.resolve(..., { skipSelf: true })` и подменяет локальные `.js`-пути на существующие `.ts`-исходники на лету.
2. **`reflect-metadata` и `pool: 'forks'`:** `apps/api/vitest.setup.ts` единожды загружает `reflect-metadata`, а **`pool: 'forks'`** запускает тесты в изолированных процессах вместо `worker_threads`, предотвращая сбои нативной регистрации `@swc/core`.
3. **`SWC_NATIVE_BINDING_CACHE` + `passThroughEnv`:** `createApiVitestConfig(include)` вызывает `ensureSwcNativeCacheDir()` **до** динамического `import('unplugin-swc')`, направляя кэш `@swc/core` в короткий путь `../../.turbo/swc` (меньше Windows `MAX_PATH`). Объявление `"passThroughEnv": ["SWC_NATIVE_BINDING_CACHE"]` в `turbo.json` не даёт Turborepo Strict Env Mode вырезать переменную кэша.

## 3. Паттерны фронтенд-тестов: React 19, `TanStack Query` и `MSW v3`

Тестирование современного Next.js App Router и React 19 требует аккуратного обращения с асинхронными таймерами, DOM-очисткой и браузерными API:

- **Явные импорты из `'vitest'` + `afterEach(cleanup)`:** без глобальных `describe`/`it`/`expect` (`globals: false`) строгий TypeScript и Biome не требуют глобальной магии. Но `@testing-library/react` вызывает автоочистку DOM только при наличии глобального `afterEach`, поэтому `apps/web/vitest.setup.ts` явно регистрирует `afterEach(() => cleanup())`, исключая «утечку» DOM-элементов между тестами.
- **Строгий перехват сети в `MSW v3`:** интеграционные тесты немедленно падают на любом незамоканном запросе к `/api/*`, вызывают `server.resetHandlers()` в `afterEach` и `server.close()` в `afterAll`.
- **Детерминированная отмена запросов при `unmount()`:** проверка подавления `AbortError` в `makeQueryClient()` монтирует `useQuery` с незавершённым `Promise` и вызывает `unmount()` без нестабильных `setTimeout`.
- **Защита `window.indexedDB` в `QueryProvider`:** явная проверка `typeof window.indexedDB !== 'undefined'` перед созданием персистера делает компонент стабильным и в SSR, и в `jsdom`-тестах.
- **Radix UI Portals в RTL:** выпадающие меню `<Select>` и диалоги `<Dialog>` рендерятся через портал напрямую в `document.body`, поэтому запросы выполняются через `screen` + `@testing-library/user-event`.

## 4. Playwright E2E: `POM`, 5 шагов `test.step`, `Zero-Cruft data-testid` и масштабируемый `WebServer`

E2E-сценарии в `apps/web/e2e/` организованы по паттерну **Page Object Model (POM)**:

```text
apps/web/e2e/
├── fixtures/app.fixture.ts            # Типизированные фикстуры GuestPassPage и SystemStatusPage
├── pages/
│   ├── guest-pass.page.ts             # Инкапсулирует модалку, ввод имени/роли и отправку формы
│   └── system-status.page.ts          # Инкапсулирует матрицу capabilities, пагинацию 2-й страницы, логи
└── specs/
    └── rbac-and-observability.spec.ts # Полный Hybrid KB + RBAC + /system-status сценарий на базе test.step()
```

### Инженерные стандарты E2E-контура

1. **Политика `Zero-Cruft data-testid`:** Playwright **никогда** не ищет элементы по переведённым текстам (`"Войти"`, `"Next"`) или хрупким HTML-тегам. Атрибуты `data-testid` (`guest-pass-dialog`, `guest-pass-submit-btn`, `leaderboard-table` и др.) добавляются **строго** к реально запрашиваемым узлам.
2. **5-шаговая телеметрия `test.step(...)` (`rbac-and-observability.spec.ts`):** каждый этап вынесен в отдельный шаг для прозрачных HTML-отчётов CI и Playwright Trace Viewer:
   1. `1. Verify public /knowledge-base/this-project article loads directly without redirect`
   2. `2. Redirect unauthenticated guest on protected KB article to GuestPassModal via Edge Proxy`
   3. `3. Issue Guest Pass and verify HttpOnly JWT cookie`
   4. `4. Land on protected MDX article and verify server-compiled content`
   5. `5. Verify /system-status Capability Matrix, Cursor Event Log, and Leaderboard Page 1 -> Page 2`
3. **Масштабируемые воркеры и serial-режим для stateful-сценариев:** `playwright.config.ts` задаёт `fullyParallel: true` (`...(process.env.CI ? { workers: 2 } : {})`), а `test.describe.configure({ mode: 'serial' })` сохраняет строгий порядок шагов в stateful-цепочке Hybrid KB ➔ auth ➔ event log.
4. **Node 24 Happy Eyeballs DNS и Next.js `webServer` (`NODE_OPTIONS`):** переменная `NODE_OPTIONS: '--dns-result-order=ipv4first --no-network-family-autoselection'` в `webServer.env` предотвращает `AggregateError` (`ECONNREFUSED ::1:4000`) при проксировании `/api/*` в IPv4-привязанный API на Node 24.

## 5. Вкладка Testing в IDE (`vitest.config.ts`) и интеграция в CI/CD

### Корневой конфиг проектов для Testing Explorer

Отдельные `vitest.config.ts` внутри пакетов ускоряют `Turborepo --affected`, а корневой `vitest.config.ts` (`projects: ['packages/*', 'apps/*']`) объединяет дерево тестов и V8-покрытие для IDE Testing Explorer (`vitest.explorer` + `ms-playwright.playwright`). Покрытие собирается командой `pnpm run test:coverage`, а интерактивный интерфейс Vitest UI поднимается через `pnpm run test:ui`.

### Интеграция в GitHub Actions CI (`.github/workflows/ci.yml`)

- **Stage 1 (`unit-tests`):** запускается параллельно с `lint`, `security` и `typecheck`, используя `prepare-codegen: "true"`, динамический `fetch-depth: '0'` с `TURBO_SCM_BASE` на PR (`turbo run test --affected` для 65 unit/integration тестов Vitest в 4 пакетах), после чего прогоняет `pnpm --filter @repo/api test:e2e` (Supertest HTTP E2E).
- **Stage 2 (`e2e`):** стартует после `needs: [ lint, typecheck, build ]`, восстанавливает кэш `.turbo`, читает точную установленную версию `@playwright/test` (`id: playwright-version` из `./apps/web/node_modules/@playwright/test/package.json`) и кэширует `~/.cache/ms-playwright` по ключу `${{ runner.os }}-playwright-${{ steps.playwright-version.outputs.version }}`. При cache miss выполняется `playwright install --with-deps chromium`, при cache hit — только системные зависимости через `playwright install-deps chromium`, затем запускается `pnpm --filter @repo/web test:e2e`, а HTML-отчёты и трейсы загружаются через `actions/upload-artifact@v7` строго при `if: failure()`.
