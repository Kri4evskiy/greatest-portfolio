## 1. Зачем современному Full-Stack приложению эшелонированная защита

В классической веб-разработке безопасность нередко откладывается «на потом» или сводится к установке пары дефолтных пакетов. Однако в архитектуре монорепозитория, объединяющего публичный интерфейс на Next.js, приватный API на NestJS, микросервисы и базу данных, компрометация одного узла может привести к падению всей системы.

В нашем проекте реализован принцип **Defense-in-Depth (Глубокоэшелонированная оборона)**:

```text
[ Браузер ]
    │
    ├── (1) HTTP Security Headers (Next.js): CSP, HSTS, X-Frame-Options, nosniff
    │
    ├── (2) Edge Auth Barrier (proxy.ts): Web Crypto HMAC-SHA256 верификация JWT
    │
    ├── (3) API Gateway Hardening (NestJS): Helmet + CORS whitelist + Throttler Guard
    │
    └── (4) Microservice Isolation: TCP :4001 в приватной Docker-сети без внешнего ingress
```

Каждый слой автономен: если злоумышленник попытается обойти клиентскую валидацию, его встретит Rate Limiter бэкенда; если попытается встроить вредоносный iframe — сработает `frame-ancestors 'none'`.

## 2. HTTP Security Headers в Next.js 16 (`apps/web/config/security-headers.config.ts`)

Настройка `Content-Security-Policy` (CSP) в современных фреймворках сопряжена с тонкими архитектурными вызовами: React Server Components, гидратация, инлайн-скрипты темы оформления для предотвращения FOUC (Flash of Unstyled Content) и живые SSE-стримы требуют точной калибровки директив.

Чтобы не перегружать конфигуратор сборки `next.config.ts` и чётко разделить инфраструктурный конфиг Next.js и слои FSD-приложения в `src/`, декларативная генерация всех заголовков безопасности была вынесена в отдельный типизированный модуль вне `src/`: `apps/web/config/security-headers.config.ts`.

```typescript title="apps/web/config/security-headers.config.ts"
export interface ContentSecurityPolicyOptions {
  allowSameOriginFraming?: boolean
}

export function buildContentSecurityPolicy(
  isProduction: boolean,
  publicApiUrl = '',
  options: ContentSecurityPolicyOptions = {},
): string {
  const { allowSameOriginFraming = false } = options
  const normalizedPublicApi = publicApiUrl.trim() ? ` ${publicApiUrl.trim()}` : ''

  // В продакшене внутренние порты инфраструктуры НИКОГДА не раскрываются в заголовках.
  // В девелопменте разрешаются порты API, микросервисов и сокеты HMR (ws/wss).
  const connectSrc = isProduction
    ? `'self' https:${normalizedPublicApi}`
    : `'self' http://localhost:4000 http://localhost:4001 http://127.0.0.1:4000 http://127.0.0.1:4001 ws: wss: https:${normalizedPublicApi}`

  // В продакшене 'unsafe-eval' полностью отключён (MDX компилируется в HAST без eval).
  // В девелопменте 'unsafe-eval' требуется для Next.js Fast Refresh.
  const scriptSrc = isProduction
    ? "'self' 'unsafe-inline'"
    : "'self' 'unsafe-inline' 'unsafe-eval'"

  const directives: string[] = [
    "default-src 'self'",
    `script-src ${scriptSrc}`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' blob: data: https:",
    "font-src 'self' data: https:",
    `connect-src ${connectSrc}`,
    "frame-src 'self'",
    `frame-ancestors ${allowSameOriginFraming ? "'self'" : "'none'"}`,
    "form-action 'self'",
    "base-uri 'self'",
    "object-src 'self'",
    ...(isProduction ? ['upgrade-insecure-requests'] : []),
  ]

  return directives.join('; ').trim()
}
```

А в самом `apps/web/next.config.ts` подключение заголовков, точечный scoping для встроенного PDF-резюме `/cv/:path+` и отключение `X-Powered-By: Next.js` выглядят так:

```typescript title="apps/web/next.config.ts"
import { getSecurityHeaders } from './config/security-headers.config'

const nextConfig: NextConfig = {
  poweredByHeader: false,
  // ...
  async headers() {
    const cvPdfAssetHeaders = getSecurityHeaders(undefined, undefined, {
      allowSameOriginFraming: true,
    })

    return [
      { source: '/(.*)', headers: getSecurityHeaders() },
      { source: '/cv/:path+', headers: cvPdfAssetHeaders },
    ]
  },
}
```

### Разбор директив и изоляция Dev/Prod:
- **Zero Port Leakage & Zero Eval в продакшене:** В проде из `connect-src` убраны порты `:4000`, `:4001` и `localhost`, а из `script-src` удалён `'unsafe-eval'` (наш HAST-движок MDX не использует `eval`/`new Function`).
- **`Cross-Origin-Opener-Policy: same-origin`:** Изолирует контекст окна браузера, блокируя доступ через `window.opener` и атаки класса Spectre/XS-Leaks.
- **`frame-ancestors 'none'` и `X-Frame-Options: DENY`:** Защищают страницы портфолио и базы знаний от атак кликджекинга (Clickjacking) — никакой сторонний сайт не сможет загрузить приложение внутри скрытого `<iframe>`.
- **SPA-безопасные `object-src 'self'`, `frame-src 'self'` и Scoped `/cv/:path+` PDF:** Так как при клиентском переходе `<Link href="/cv">` из `/` или `/knowledge-base` в Next.js App Router браузер не перезагружает HTML-документ и сохраняет CSP стартовой страницы, директивы `object-src 'self'` и `frame-src 'self'` включены на уровне документа, но на всех маршрутах сайта (`/(.*)`) стоят `frame-ancestors 'none'` и `X-Frame-Options: DENY`, и **только** для статических PDF-файлов `/cv/:path+` разрешены `frame-ancestors 'self'` и `X-Frame-Options: SAMEORIGIN`. Благодаря этому встроенный `<object type="application/pdf">` безотказно открывается при SPA-переходах, но никакой внешний объект или другой внутренний роут не может быть встроен.
- **`base-uri 'self'`:** Предотвращает инъекцию тега `<base href="...">`, эксплуатируемую для перехвата относительных ссылок.
- **`Strict-Transport-Security (HSTS)`:** Заголовок `max-age=63072000; includeSubDomains; preload` отдаётся только в продакшене и указывает браузеру форсировать HTTPS на протяжении 2 лет.
- **`Permissions-Policy`:** Запрещает доступ к камере, микрофону, геолокации и алгоритмам трекинга интересов браузера (`camera=(), microphone=(), geolocation=(), browsing-topics=()`).

## 3. Защита API-шлюза в NestJS 12: Helmet с поддержкой SSE

Бэкенд `apps/api` построен на платформе NestJS 12 с Express-адаптером. Для базовой защиты заголовков HTTP подключена библиотека `helmet`.

Однако стандартная конфигурация `helmet()` по умолчанию включает `Cross-Origin-Resource-Policy: same-origin`. В архитектуре монорепозитория, где фронтенд (Next.js на порту `3000` или Vercel-домене) обращается к API (порт `4000` или Render-домен) и держит постоянное соединение `EventSource` с эндпоинтом `@Sse('stream')`, дефолтная политика приведёт к блокировке стрима браузером.

Решение реализовано в `apps/api/src/main.ts` (включая `trust proxy: 1` для корректного определения IP клиента за обратным прокси и строгий CORS по окружению):

```typescript title="apps/api/src/main.ts"
import type { NestExpressApplication } from '@nestjs/platform-express'
import cookieParser from 'cookie-parser'
import helmet from 'helmet'

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create<NestExpressApplication>(AppModule)
  const isProduction = process.env.NODE_ENV === 'production'

  if (isProduction) {
    app.set('trust proxy', 1)
  }

  app.setGlobalPrefix('api')
  app.use(
    helmet({
      crossOriginResourcePolicy: { policy: 'cross-origin' },
      contentSecurityPolicy: false,
    }),
  )
  app.use(cookieParser())

  const webOrigin = process.env.WEB_ORIGIN ?? 'http://localhost:3000'
  const allowedOrigins = isProduction
    ? webOrigin
        .split(',')
        .map((origin) => origin.trim())
        .filter(Boolean)
    : [webOrigin, 'http://127.0.0.1:3000']

  app.enableCors({
    origin: allowedOrigins,
    credentials: true,
    methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  })

  // ...
}
```

> [!NOTE] Почему `contentSecurityPolicy: false` на уровне API
> Бэкенд NestJS работает в режиме Pure REST & SSE API, возвращая структурированный JSON и потоки событий. CSP предназначен для HTML-документов в браузере, поэтому генерация заголовков CSP на API избыточна и отключается в пользу полноценной защиты на уровне Next.js.

## 4. Защита от брутфорса: `@nestjs/throttler`

Одной из самых критических точек входа является форма гостевого доступа и админского логина (`GuestPassModal`). Без rate limiting злоумышленник или автоматизированный ботнет мог бы за секунды перебрать секретный пасскод администратора (`ADMIN_SECRET_PASSCODE`).

Для устранения этой уязвимости мы внедрили `@nestjs/throttler`:

### 1. Подключение модуля в `AppModule`:

```typescript title="apps/api/src/app.module.ts"
import { APP_GUARD } from '@nestjs/core'
import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler'

@Module({
  imports: [
    ThrottlerModule.forRoot([
      {
        ttl: 60000, // Скользящее окно: 60 секунд
        limit: 100,  // Базовый лимит на общие API-вызовы
      },
    ]),
    // ...
  ],
  providers: [
    {
      provide: APP_GUARD,
      useClass: ThrottlerGuard,
    },
  ],
})
export class AppModule {}
```

### 2. Строгий лимит на эндпоинты авторизации:

В `AuthController` эндпоинты `POST /api/auth/guest-pass` и `POST /api/auth/login` защищены персональным лимитом — **максимум 5 запросов за 60 секунд**:

```typescript title="apps/api/src/modules/auth/auth.controller.ts"
@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('guest-pass')
@HttpCode(HttpStatus.OK)
async issueGuestPass(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  // Выпуск токена и установка HttpOnly куки
}

@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('login')
@HttpCode(HttpStatus.OK)
async login(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  return this.issueGuestPass(body, req, res)
}
```

### 3. Исключение фонового SSE-стрима:

Постоянное соединение Server-Sent Events (`GET /api/telemetry/stream`) не должно разрываться из-за глобального лимитера, поэтому декоратор `@SkipThrottle()` применён **точечно к методу** `streamEvents()`, оставляя `GET /api/telemetry/stats` под защитой глобального лимита:

```typescript title="apps/api/src/modules/telemetry/telemetry.controller.ts"
@Controller('telemetry')
export class TelemetryController {
  @SkipThrottle()
  @Sse('stream')
  streamEvents(): Observable<MessageEvent> {
    return this.telemetryService.getEventStream()
  }
}
```

### 4. Архитектурная эволюция: In-Memory Throttler ➔ Distributed Redis Throttler

В текущей конфигурации одиночного контейнера `@nestjs/throttler` хранит счетчики IP в оперативной памяти процесса Node.js. Это гарантирует максимальную производительность (наносекундный доступ) и нулевую стоимость инфраструктуры ($0).

Однако при горизонтальном масштабировании (запуск нескольких реплик `apps/api` за балансировщиком нагрузки) память инстансов изолирована. Чтобы злоумышленник не мог обойти лимит, распределяя запросы между репликами, архитектура спроектирована под бесшовное подключение **Redis (Upstash / Docker)**:
- Подключается `ThrottlerStorageRedisService` поверх `ioredis` со скользящим окном;
- Все реплики API оперируют единым атомарным счетчиком в RAM;
- Реализуется паттерн **Graceful Degradation**: при отсутствии переменной `REDIS_URL` бэкенд прозрачно использует локальный In-Memory сторадж без сбоев.

## 5. Итоги и чек-лист защищенности

Внедренный комплекс мер обеспечивает уровень защиты **A+** по стандартам SecurityHeaders и Mozilla Observatory:

| Вектор угрозы                | Механизм защиты в монорепозитории                                          | Статус       |
| :--------------------------- | :------------------------------------------------------------------------- | :----------- |
| **Кража сессии через XSS**   | `HttpOnly` куки + Zero-Eval HAST + санитизация `classifySafeMarkdownLink`  | 🛡️ Защищено |
| **Clickjacking**             | `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` (scoped `/cv/:path+`) | 🛡️ Защищено |
| **Passcode Brute-Force**     | `@nestjs/throttler`: 5 попыток / 60 сек на IP + HTTP 429 Too Many Requests | 🛡️ Защищено |
| **MIME Sniffing**            | `X-Content-Type-Options: nosniff`                                          | 🛡️ Защищено |
| **Man-in-the-Middle (MitM)** | HSTS (`max-age=63072000; includeSubDomains; preload`)                      | 🛡️ Защищено |
| **Cross-Service Leakage**    | Изоляция TCP `:4001` в закрытой сети Docker Compose                        | 🛡️ Защищено |

### Осознанные архитектурные компромиссы (Engineering Trade-offs)

Ни одна продакшен-архитектура не обходится без компромиссов между безопасностью, производительностью и UX. Ниже зафиксированы три осознанных инженерных решения текущей реализации и способы компенсации их рисков:

1. **Статическая генерация `SSG` (`'unsafe-inline'`) против динамического `CSP Nonce`:**
   - *Компромисс:* Полный отказ от `'unsafe-inline'` в `script-src` требует генерации уникального криптографического `nonce` на каждый HTTP-запрос. В Next.js 16 использование `nonce` принудительно отключает **Static Site Generation (`SSG`)** и переводит все 137 маршрутов в динамический `SSR`, лишая платформу CDN-кэширования и отдачи страниц за `15–20 мс`.
   - *Компенсация риска:* Приложение не рендерит пользовательский UGC-контент в HTML (все `.mdx` статьи живут в репозитории, компилируются через Zero-Eval HAST-пайплайн с вырезанием сырого HTML и проверкой протоколов ссылок через `classifySafeMarkdownLink`), а сессионный токен изолирован в `HttpOnly` куке (недоступной из `document.cookie`), поэтому сохранение `SSG` является оправданным архитектурным выбором.
2. **Публичный индекс дискавери `Cmd+K` (`/search-index/[locale]`) против закрытых тел статей:**
   - *Компромисс:* В `apps/web/src/proxy.ts` маршрут `/search-index/[locale]` намеренно исключён из-под проверки JWT (`matcher: ['/((?!api|search-index|_next|_vercel|.*\\..*).*)']`), чтобы рекрутеры и тимлиды могли пользоваться глобальным поиском `Cmd+K` прямо с главной страницы до получения `Guest Pass`.
   - *Компенсация риска:* В статический JSON-индекс попадают только витринные метаданные (`title`, `summary`, `#теги` и заголовки секций `h2/h3`), тогда как сами тексты и код конспектов в `/knowledge-base/*` закрыты криптографической проверкой `HMAC-SHA256` на Edge.
3. **Stateless-проверка JWT на Edge против мгновенного отзыва сессий (До внедрения Redis):**
   - *Компромисс:* Функция `verifyEdgeJwtHs256` в `proxy.ts` проверяет подпись и `exp` за `< 0.2 мс` без обращения к базе данных. Из-за этого выписанный 7-дневный токен нельзя точечно отозвать на уровне Edge до истечения его срока жизни без смены `JWT_SECRET`.
   - *Компенсация риска:* В планах развития (Post-MVP Roadmap) заложен переход на связку короткоживущего `Access` (`15m`) + ротируемого `HttpOnly Refresh` (`7d`) токенов с хранением активных сессий в `VisitorSession` (`PostgreSQL`) и распределённым кэшем в **Redis**.
