## 1. Multi-Stage Build Pipeline (`pruner -> builder -> runner`)

To keep source files, compilers, and unrelated workspace packages out of production images, every Dockerfile in `docker/` separates container construction into three deterministic stages:

1. **`pruner`:** runs `turbo prune @repo/<app> --docker` to emit the minimal subgraph (`out/json/`, `out/full/`, `out/pnpm-lock.yaml`) needed by the target service.
2. **`builder`:** activates `pnpm@12.18.0`, runs `pnpm install --frozen-lockfile --ignore-scripts` with a shared BuildKit cache mount, runs `pnpm turbo run build --filter=@repo/<app>...`, and prunes `devDependencies`.
3. **`runner`:** copies only compiled artifacts (`dist/` or `.next/standalone`) and executes under a non-root user (`USER node` / `USER nextjs`).

---

## 2. `turbo prune` & Shared BuildKit Cache Mount

When building multiple containers from one monorepo, `out/json/` keeps the dependency installation layer cached across code changes, while mounting `/root/.local/share/pnpm/store` with BuildKit `type=cache,id=pnpm` downloads shared packages once and reuses them across all service builds:

```dockerfile title="docker/api.Dockerfile"
FROM node:22-alpine AS pruner
RUN apk add --no-cache libc6-compat openssl
ENV DO_NOT_TRACK=1
ENV TURBO_TELEMETRY_DISABLED=1
RUN npm install -g turbo@^2
WORKDIR /app
COPY . .
RUN turbo prune @repo/api --docker

FROM node:22-alpine AS builder
RUN apk add --no-cache libc6-compat openssl
ENV DO_NOT_TRACK=1
ENV TURBO_TELEMETRY_DISABLED=1
RUN corepack enable && corepack prepare pnpm@12.18.0 --activate && pnpm --version
WORKDIR /app

COPY --from=pruner /app/out/json/ .
COPY --from=pruner /app/out/pnpm-lock.yaml ./pnpm-lock.yaml
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile --ignore-scripts
```

## 3. Pruning `devDependencies` While Preserving `.prisma/client`

In the `builder` stage, `pnpm turbo run build --filter=@repo/api...` generates the Prisma client and compiles TypeScript. Before calling `pnpm prune --prod --ignore-scripts`, the generated `.prisma` and `@prisma/client` artifacts are staged in `/tmp` and restored afterward so the compiled query engine remains intact in production:

```dockerfile title="docker/api.Dockerfile"
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm turbo run build --filter=@repo/api... && \
    cp -R /app/node_modules/.pnpm/@prisma+client*/node_modules/.prisma /tmp/.prisma && \
    cp -R /app/node_modules/.pnpm/@prisma+client*/node_modules/@prisma/client /tmp/prisma-client && \
    pnpm prune --prod --ignore-scripts && \
    cp -R /tmp/.prisma /app/node_modules/.pnpm/@prisma+client*/node_modules/ && \
    cp -R /tmp/prisma-client/* /app/node_modules/.pnpm/@prisma+client*/node_modules/@prisma/client/ && \
    rm -rf /tmp/.prisma /tmp/prisma-client
```

### Production Image Profiles

| Container | Base Image | Port Scope | Runtime User |
| :--- | :---: | :---: | :---: |
| `workfolio-telemetry-ms` | `node:22-alpine` | `4001` (internal network only) | `node` (non-root) |
| `workfolio-api` | `node:22-alpine` | `4000` | `node` (non-root) |
| `workfolio-web` (`standalone`) | `node:22-alpine` | `3000` | `nextjs` (`UID 1001`) |

> [!TIP]
> Because the production `api` image excludes `Prisma CLI`, database schema migrations (`prisma migrate deploy`) run as a dedicated CI/CD step before rolling out new containers.
