## 1. Чому сучасний Full-Stack додаток потребує ешелонованого захисту

У звичайній веб-розробці безпеку нерідко відкладають «на потім» або зводять до підключення дефолтних пакетів. Проте в архітектурі монорепозиторію, який об'єднує публічний інтерфейс на Next.js, приватний API на NestJS, мікросервіси та базу даних, компрометація одного вузла здатна зруйнувати всю систему.

У нашому проєкті реалізовано принцип **Defense-in-Depth (Глибокоешелонована оборона)**:

```text
[ Браузер ]
    │
    ├── (1) HTTP Security Headers (Next.js): CSP, HSTS, X-Frame-Options, nosniff
    │
    ├── (2) Edge Auth Barrier (proxy.ts): Web Crypto HMAC-SHA256 верифікація JWT
    │
    ├── (3) API Gateway Hardening (NestJS): Helmet + CORS whitelist + Throttler Guard
    │
    └── (4) Microservice Isolation: TCP :4001 у приватній Docker-мережі без зовнішнього ingress
```

Кожен шар є повністю автономним: якщо зловмисник спробує обійти клієнтську валідацію, його зупинить Rate Limiter бекенду; якщо спробує вбудувати несанкціонований iframe — спрацює `frame-ancestors 'none'`.

## 2. HTTP Security Headers у Next.js 16 (`apps/web/config/security-headers.config.ts`)

Конфігурація `Content-Security-Policy` (CSP) у сучасних фреймворках має низку тонких архітектурних викликів: React Server Components, SSR-гідратація, інлайн-скрипти теми оформлення для запобігання FOUC (Flash of Unstyled Content) та живі SSE-стріми вимагають точного калібрування директив.

Щоб не перевантажувати конфігуратор збірки `next.config.ts` і чітко розділити інфраструктурний конфіг Next.js та шари FSD-застосунку в `src/`, декларативну генерацію всіх заголовків безпеки було винесено в окремий типізований модуль поза `src/`: `apps/web/config/security-headers.config.ts`.

```typescript title="apps/web/config/security-headers.config.ts"
export interface ContentSecurityPolicyOptions {
  allowSameOriginFraming?: boolean
}

export function buildContentSecurityPolicy(
  isProduction: boolean,
  publicApiUrl = '',
  options: ContentSecurityPolicyOptions = {},
): string {
  const { allowSameOriginFraming = false } = options
  const normalizedPublicApi = publicApiUrl.trim() ? ` ${publicApiUrl.trim()}` : ''

  // У продакшені внутрішні порти інфраструктури НІКОЛИ не розкриваються в заголовках.
  // У девелопменті дозволяються порти API, мікросервісів та сокети HMR (ws/wss).
  const connectSrc = isProduction
    ? `'self' https:${normalizedPublicApi}`
    : `'self' http://localhost:4000 http://localhost:4001 http://127.0.0.1:4000 http://127.0.0.1:4001 ws: wss: https:${normalizedPublicApi}`

  // У продакшені 'unsafe-eval' повністю вимкнений (MDX компілюється в HAST без eval).
  // У девелопменті 'unsafe-eval' потрібен для Next.js Fast Refresh.
  const scriptSrc = isProduction
    ? "'self' 'unsafe-inline'"
    : "'self' 'unsafe-inline' 'unsafe-eval'"

  const directives: string[] = [
    "default-src 'self'",
    `script-src ${scriptSrc}`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' blob: data: https:",
    "font-src 'self' data: https:",
    `connect-src ${connectSrc}`,
    "frame-src 'self'",
    `frame-ancestors ${allowSameOriginFraming ? "'self'" : "'none'"}`,
    "form-action 'self'",
    "base-uri 'self'",
    "object-src 'self'",
    ...(isProduction ? ['upgrade-insecure-requests'] : []),
  ]

  return directives.join('; ').trim()
}
```

А в самому `apps/web/next.config.ts` підключення заголовків, точковий scoping для вбудованого PDF-резюме `/cv/:path+` та вимкнення `X-Powered-By: Next.js` виглядають так:

```typescript title="apps/web/next.config.ts"
import { getSecurityHeaders } from './config/security-headers.config'

const nextConfig: NextConfig = {
  poweredByHeader: false,
  // ...
  async headers() {
    const cvPdfAssetHeaders = getSecurityHeaders(undefined, undefined, {
      allowSameOriginFraming: true,
    })

    return [
      { source: '/(.*)', headers: getSecurityHeaders() },
      { source: '/cv/:path+', headers: cvPdfAssetHeaders },
    ]
  },
}
```

### Розбір директив та ізоляція Dev/Prod:
- **Zero Port Leakage та Zero Eval у продакшені:** У проді з `connect-src` видалені порти `:4000`, `:4001` та `localhost`, а з `script-src` прибрано `'unsafe-eval'` (наш HAST-рушій MDX не використовує `eval`/`new Function`).
- **`Cross-Origin-Opener-Policy: same-origin`:** Ізолює контекст вікна браузера, блокуючи доступ через `window.opener` і атаки класу Spectre/XS-Leaks.
- **`frame-ancestors 'none'` та `X-Frame-Options: DENY`:** Захищають портфоліо та базу знань від атак клікджекінгу (Clickjacking) — сторонній сайт не зможе завантажити застосунок у прихованому `<iframe>`.
- **SPA-безпечні `object-src 'self'`, `frame-src 'self'` та Scoped `/cv/:path+` PDF:** Оскільки при клієнтському переході `<Link href="/cv">` із `/` або `/knowledge-base` у Next.js App Router браузер не перезавантажує HTML-документ і зберігає CSP стартової сторінки, директиви `object-src 'self'` і `frame-src 'self'` увімкнено на рівні документа, але на всіх маршрутах сайту (`/(.*)`) стоять `frame-ancestors 'none'` та `X-Frame-Options: DENY`, і **лише** для статичних PDF-файлів `/cv/:path+` дозволені `frame-ancestors 'self'` та `X-Frame-Options: SAMEORIGIN`. Завдяки цьому вбудований `<object type="application/pdf">` безвідмовно відкривається при SPA-переходах, але жоден зовнішній об'єкт чи інший внутрішній роут не може бути вбудований.
- **`base-uri 'self'`:** Запобігає маніпуляціям із тегом `<base href="...">`.
- **`Strict-Transport-Security (HSTS)`:** Заголовок `max-age=63072000; includeSubDomains; preload` віддається лише в продакшені й вказує браузеру форсувати HTTPS протягом 2 років.
- **`Permissions-Policy`:** Забороняє доступ до камери, мікрофона, геолокації та когорт трекінгу інтересів браузера (`camera=(), microphone=(), geolocation=(), browsing-topics=()`).

## 3. Захист API-шлюзу в NestJS 12: Helmet з підтримкою SSE

Бекенд `apps/api` побудований на платформі NestJS 12 з Express-адаптером. Для базового захисту заголовків HTTP підключено бібліотеку `helmet`.

Проте стандартна конфігурація `helmet()` за замовчуванням вмикає `Cross-Origin-Resource-Policy: same-origin`. В архітектурі монорепозиторію, де фронтенд (Next.js на порту `3000` або Vercel-домені) звертається до API (порт `4000` або Render-домен) і тримає відкрите з'єднання `EventSource` з ендпоінтом `@Sse('stream')`, дефолтна політика призведе до блокування стріму браузером.

Рішення реалізовано в `apps/api/src/main.ts` (разом із `trust proxy: 1` для точного визначення IP за зворотним проксі та суворим CORS по середовищу):

```typescript title="apps/api/src/main.ts"
import type { NestExpressApplication } from '@nestjs/platform-express'
import cookieParser from 'cookie-parser'
import helmet from 'helmet'

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create<NestExpressApplication>(AppModule)
  const isProduction = process.env.NODE_ENV === 'production'

  if (isProduction) {
    app.set('trust proxy', 1)
  }

  app.setGlobalPrefix('api')
  app.use(
    helmet({
      crossOriginResourcePolicy: { policy: 'cross-origin' },
      contentSecurityPolicy: false,
    }),
  )
  app.use(cookieParser())

  const webOrigin = process.env.WEB_ORIGIN ?? 'http://localhost:3000'
  const allowedOrigins = isProduction
    ? webOrigin
        .split(',')
        .map((origin) => origin.trim())
        .filter(Boolean)
    : [webOrigin, 'http://127.0.0.1:3000']

  app.enableCors({
    origin: allowedOrigins,
    credentials: true,
    methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  })

  // ...
}
```

> [!NOTE] Чому `contentSecurityPolicy: false` на рівні API
> Бекенд NestJS функціонує в режимі Pure REST & SSE API, повертаючи структурований JSON і потоки подій. CSP призначений для HTML-документів у браузері, тому генерація заголовків CSP на API є надлишковою і відключається на користь захисту на рівні Next.js.

## 4. Захист від брутфорсу: `@nestjs/throttler`

Однією з найбільш критичних точок входу є форма гостьового доступу та адмінського логіну (`GuestPassModal`). Без rate limiting автоматизований ботнет міг би за секунди перебрати секретний паскод адміністратора (`ADMIN_SECRET_PASSCODE`).

Для усунення цієї вразливості ми впровадили `@nestjs/throttler`:

### 1. Підключення модуля в `AppModule`:

```typescript title="apps/api/src/app.module.ts"
import { APP_GUARD } from '@nestjs/core'
import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler'

@Module({
  imports: [
    ThrottlerModule.forRoot([
      {
        ttl: 60000, // Ковзне вікно: 60 секунд
        limit: 100,  // Базовий ліміт на звичайні API-виклики
      },
    ]),
    // ...
  ],
  providers: [
    {
      provide: APP_GUARD,
      useClass: ThrottlerGuard,
    },
  ],
})
export class AppModule {}
```

### 2. Суворий ліміт на ендпоінти авторизації:

В `AuthController` ендпоінти `POST /api/auth/guest-pass` та `POST /api/auth/login` захищені лімітом — **не більше 5 запитів за 60 секунд**:

```typescript title="apps/api/src/modules/auth/auth.controller.ts"
@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('guest-pass')
@HttpCode(HttpStatus.OK)
async issueGuestPass(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  // Випуск токена та встановлення HttpOnly куки
}

@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('login')
@HttpCode(HttpStatus.OK)
async login(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  return this.issueGuestPass(body, req, res)
}
```

### 3. Виключення фонового SSE-стріму:

Постійне з'єднання Server-Sent Events (`GET /api/telemetry/stream`) не повинно розриватися через загальний лімітер, тому декоратор `@SkipThrottle()` застосовано **точково до методу** `streamEvents()`, залишаючи `GET /api/telemetry/stats` під захистом загальної квоти:

```typescript title="apps/api/src/modules/telemetry/telemetry.controller.ts"
@Controller('telemetry')
export class TelemetryController {
  @SkipThrottle()
  @Sse('stream')
  streamEvents(): Observable<MessageEvent> {
    return this.telemetryService.getEventStream()
  }
}
```

### 4. Архітектурна еволюція: In-Memory Throttler ➔ Distributed Redis Throttler

У поточній конфігурації одиночного інстансу `@nestjs/throttler` зберігає лічильники IP в оперативній пам'яті процесу Node.js. Це забезпечує наносекундну швидкість і нульову вартість інфраструктури ($0).

Проте при горизонтальному масштабуванні (запуск кількох реплік `apps/api` за балансувальником навантаження) пам'ять інстансів ізольована. Щоб зловмисник не міг обійти квоту, розподіляючи запити між репліками, архітектура спроєктована під безшовний перехід на **Redis (Upstash / Docker)**:
- Підключається `ThrottlerStorageRedisService` поверх `ioredis` із ковзним вікном;
- Усі репліки API синхронізуються через єдиний атомарний лічильник у RAM;
- Реалізується патерн **Graceful Degradation**: за відсутності змінної `REDIS_URL` бекенд прозоро використовує локальний In-Memory сторадж без збоїв.

## 5. Підсумки та чек-лист захищеності

Впроваджений комплекс заходів забезпечує рівень захисту **A+** за стандартами SecurityHeaders і Mozilla Observatory:

| Вектор загрози               | Механізм захисту в монорепозиторії                                         | Статус     |
| :--------------------------- | :------------------------------------------------------------------------- | :--------- |
| **Крадіжка сесії через XSS** | `HttpOnly` куки + Zero-Eval HAST + санітизація `classifySafeMarkdownLink`  | 🛡️ Захищено |
| **Clickjacking**             | `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` (scoped `/cv/:path+`) | 🛡️ Захищено |
| **Passcode Brute-Force**     | `@nestjs/throttler`: 5 спроб / 60 сек на IP + HTTP 429 Too Many Requests   | 🛡️ Захищено |
| **MIME Sniffing**            | `X-Content-Type-Options: nosniff`                                          | 🛡️ Захищено |
| **Man-in-the-Middle (MitM)** | HSTS (`max-age=63072000; includeSubDomains; preload`)                      | 🛡️ Захищено |
| **Cross-Service Leakage**    | Ізоляція TCP `:4001` у закритій мережі Docker Compose                      | 🛡️ Захищено |

### Усвідомлені архітектурні компроміси (Engineering Trade-offs)

Жодна продакшен-архітектура не обходиться без компромісів між безпекою, продуктивністю та UX. Нижче зафіксовані три усвідомлені інженерні рішення поточної реалізації та способи компенсації їхніх ризиків:

1. **Статична генерація `SSG` (`'unsafe-inline'`) проти динамічного `CSP Nonce`:**
   - *Компроміс:* Повна відмова від `'unsafe-inline'` у `script-src` вимагає генерації унікального криптографічного `nonce` на кожен HTTP-запит. У Next.js 16 використання `nonce` примусово вимикає **Static Site Generation (`SSG`)** і переводить усі 137 маршрутів у динамічний `SSR`, позбавляючи платформу CDN-кешування та віддачі сторінок за `15–20 мс`.
   - *Компенсація ризику:* Застосунок не рендерить користувацький UGC-контент у HTML (усі `.mdx` статті живуть у репозиторії, компілюються через Zero-Eval HAST-пайплайн із вирізанням сирого HTML і перевіркою протоколів посилань через `classifySafeMarkdownLink`), а сесійний токен ізольований у `HttpOnly` куці (недоступній із `document.cookie`), тому збереження `SSG` є виправданим архітектурним вибором.
2. **Публічний індекс діскавері `Cmd+K` (`/search-index/[locale]`) проти закритих тіл статей:**
   - *Компроміс:* У `apps/web/src/proxy.ts` маршрут `/search-index/[locale]` навмисно виключений з-під перевірки JWT (`matcher: ['/((?!api|search-index|_next|_vercel|.*\\..*).*)']`), щоб рекрутери й тімліди могли користуватися глобальним пошуком `Cmd+K` просто з головної сторінки до отримання `Guest Pass`.
   - *Компенсація ризику:* До статичного JSON-індексу потрапляють лише вітринні метадані (`title`, `summary`, `#теги` та заголовки секцій `h2/h3`), тоді як самі тексти й код конспектів у `/knowledge-base/*` закриті криптографічною перевіркою `HMAC-SHA256` на Edge.
3. **Stateless-перевірка JWT на Edge проти миттєвого відкликання сесій (До впровадження Redis):**
   - *Компроміс:* Функція `verifyEdgeJwtHs256` у `proxy.ts` перевіряє підпис та `exp` за `< 0.2 мс` без звернення до бази даних. Через це виписаний 7-денний токен не можна точково відкликати на рівні Edge до закінчення терміну його дії без зміни `JWT_SECRET`.
   - *Компенсація ризику:* У планах розвитку (Post-MVP Roadmap) закладено перехід на зв'язку короткоживучого `Access` (`15m`) + ротованого `HttpOnly Refresh` (`7d`) токенів зі збереженням активних сесій у `VisitorSession` (`PostgreSQL`) та розподіленим кешем у **Redis**.
