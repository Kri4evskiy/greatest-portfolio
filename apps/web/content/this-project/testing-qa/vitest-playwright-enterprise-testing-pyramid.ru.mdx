## 1. Архитектура нашей 3-уровневой пирамиды тестирования

Вместо медленных E2E-тестов для проверки чистой логики или чрезмерного мокирования всего фреймворка каждый слой монорепозитория тестируется самым лёгким инструментом, сохраняющим реальную семантику выполнения:

```text
                        ▲
                       / \
                      /   \    Уровень 3: Playwright POM E2E (apps/web/e2e/)
                     / E2E \   Реальный Chromium + собранный Next.js 16 + NestJS 12 webServer
                    /-------\
                   /  HTTP   \ Уровень 2: NestJS AppModule + Supertest и RTL + MSW v3
                  /  и UI Int \ Реальные DI/Guards/Pipes/Filters и TanStack Query + MSW v3
                 /-------------\
                /   Unit и Zod  \ Уровень 1: Изолированный Vitest (shared-schemas, web, api)
               /_________________\ Контракты схем, Zustand, Axios-клиент, Prisma fallback
```

| Слой | Раннер и библиотеки | Область и путь | Что гарантирует |
| :--- | :--- | :--- | :--- |
| **Контракты (`Tier 1`)** | `Vitest` (Node) | `packages/shared-schemas/src/__tests__/` | `resolveEndpoint`, границы Zod-схем пагинации, целостность всех 16 локализованных ADR |
| **Web Unit (`Tier 1`)** | `Vitest` (`node` + `jsdom`) | `apps/web/src/shared/**/__tests__/` | `Axios`, Edge Web Crypto `verifyEdgeJwtHs256`, `QueryClient`, `APP_ROUTES`, `useUIStore` |
| **Web Integration (`Tier 2`)** | `Vitest` + `RTL` + `MSW v3` | `apps/web/src/features/**/__tests__/` | Пагинация, фильтры категорий и сортировка через реальный `TanStack Query` |
| **API Unit (`Tier 1`)** | `Vitest` + `unplugin-swc` | `apps/api/src/**/__tests__/*.spec.ts` | `app.config`, защита от CRLF `request-id`, `PrismaService` fallback, `AuthService` / `JwtRolesGuard` |
| **Telemetry Unit (`Tier 1`)** | `Vitest` (Node + `@vitest/coverage-v8`) | `apps/telemetry-ms/src/__tests__/` | `TelemetryMicroserviceController`: Zod-фильтрация, буфер на 50 событий и `getStats()` |
| **API HTTP E2E (`Tier 2`)** | `Vitest` + `Supertest` | `apps/api/test/*.e2e-spec.ts` | Полный `AppModule` (`CORS`, `CookieParser`, `ThrottlerGuard`, `ValidationPipe`, `HttpOnly` JWT) |
| **Browser E2E (`Tier 3`)** | `Playwright` Chromium | `apps/web/e2e/{fixtures,pages,specs}/` | Edge `src/proxy.ts` JWT-верификация, разблокировка `GuestPassModal`, инспектор `/system-status` |

### Кто за что отвечает: различия между `Vitest`, `SWC`, `MSW v3`, `Supertest` и `Playwright`

Удобнее всего представить тестовую систему как конвейер, где каждый инструмент решает строго одну задачу и не подменяет остальные:

1. **`Vitest` (тест-раннер и движок проверок):**
   Находит тестовые файлы, предоставляет `describe / it / expect`, изолирует воркеры и собирает отчёты покрытия V8. Сам по себе он не компилирует метаданные NestJS, не перехватывает HTTP-запросы и не открывает браузер.
2. **`SWC` (`@swc/core` + `unplugin-swc` — Rust-компилятор для NestJS-тестов):**
   Это не тестовый фреймворк, а быстрый компилятор `TypeScript ➔ JavaScript`. Стандартный транспилятор внутри Vite вырезает метаданные декораторов (`emitDecoratorMetadata`), из-за чего NestJS ломается при внедрении зависимостей (DI). `SWC` сохраняет эти метаданные на скорости Rust, позволяя запускать реальные NestJS-модули внутри `Vitest`.
3. **`MSW v3` (Mock Service Worker — сетевой перехватчик для фронтенда):**
   Используется в интеграционных тестах `apps/web` (`React 19` + `TanStack Query` + `Axios`). Компонент честно отправляет настоящий HTTP-запрос на `/api/knowledge/metrics/paginated`, а `MSW` перехватывает его на границе сети в памяти и возвращает заготовленный JSON. Это позволяет проверить реальную пагинацию, фильтры, ретраи и кэширование UI без поднятого бэкенда.
4. **`Supertest` (in-memory HTTP-клиент для бэкенда):**
   Используется в HTTP E2E-тестах `apps/api`. Поднимает реальный `AppModule` NestJS в памяти и отправляет настоящие HTTP-запросы (`GET /api/capabilities`, `POST /api/auth/guest-pass`), проверяя статус-коды, `Set-Cookie`, `ZodValidationPipe`, `JwtRolesGuard` и фильтры ошибок — без запуска браузера и фронтенда.
5. **`Playwright` (настоящий браузер Chromium):**
   Запускает собранные production-серверы Next.js и NestJS и проходит пользовательские сценарии целиком: от редиректов Edge Proxy и `HttpOnly`-кук до рендера `.mdx`-статей и пагинации `/system-status`.

**Если коротко:**
- **`Vitest`** — запускает тесты и проверяет `expect(...)`.
- **`SWC`** — компилирует NestJS TypeScript-код для `Vitest` с сохранением декораторов.
- **`MSW v3`** — подменяет ответы сервера на уровне сети для тестов фронтенда.
- **`Supertest`** — шлёт HTTP-запросы в настоящий NestJS `AppModule` без фронтенда.
- **`Playwright`** — открывает реальный браузер и тестирует весь стек целиком.

> [!NOTE]
> **Роль `Storybook 10` (`@repo/ui`) vs `Vitest` / `Playwright`:** UI-примитивы изолированы в `packages/ui/` и визуально тестируются в Storybook без привязки к бизнес-API. Сетевые сценарии, кэширование, RBAC-редиректы и гидрация живут в `Vitest` + `Playwright`.

## 2. Почему `Vitest` + `unplugin-swc` заменили `Jest` и `ts-jest`

Наш монорепозиторий работает на **`TypeScript 7` + нативном `ESM` (`"type": "module"`)**, где классический стек `Jest` сталкивается с двумя системными ограничениями:

1. **Привязка `ts-jest` к старому компилятору:** `ts-jest` завязан на legacy JS API компилятора (`typescript <7`) и требует хрупких экспериментальных флагов VM для нативного ESM.
2. **Метаданные декораторов NestJS (`emitDecoratorMetadata`) в ESM:** встроенный в Vite транспилятор (`esbuild` / `oxc`) вырезает `design:paramtypes`, без которых ломается Dependency Injection NestJS (`ConfigService`, `JwtService`, `PrismaService`). Подключение **`unplugin-swc`** в `apps/api/vitest.base.ts` сохраняет метаданные декораторов на скорости Rust.

```ts title="apps/api/vitest.base.ts"
function resolveTsExtensionPlugin(): Plugin {
  return {
    name: 'resolve-ts-extensions',
    enforce: 'pre',
    resolveId(source, importer) {
      if (!importer || !source.startsWith('.') || !source.endsWith('.js')) return null
      const base = path.resolve(path.dirname(importer), source.slice(0, -3))
      for (const ext of ['.ts', '.tsx']) {
        if (fs.existsSync(base + ext)) return base + ext
      }
      return null
    },
  }
}
```

### Три обязательные тонкости Vitest для NestJS 12

1. **Резолвер расширений `.js` ➔ `.ts`:** при `moduleResolution: "NodeNext"` TypeScript-файлы импортируют локальные модули как `./auth.service.js`. `tsc` понимает это при компиляции в `dist/`, а Vite в runtime тестов читает исходники напрямую — поэтому `resolveTsExtensionPlugin()` преобразует относительные `.js`-пути в `.ts` на лету.
2. **`reflect-metadata` и `pool: 'forks'`:** `apps/api/vitest.setup.ts` единожды загружает `reflect-metadata`, а **`pool: 'forks'`** запускает тесты в изолированных процессах вместо `worker_threads`, предотвращая сбои нативной регистрации `@swc/core`.
3. **`SWC_NATIVE_BINDING_CACHE` + `passThroughEnv`:** в Windows-песочницах и средах с ограничением длины пути (`MAX_PATH`) или прав на `%LOCALAPPDATA%\swc` падает загрузка бинарника `@swc/core@1.16`. Короткий fallback `.turbo/swc` в `vitest.base.ts` в связке с `"passThroughEnv": ["SWC_NATIVE_BINDING_CACHE"]` в `turbo.json` не даёт Turborepo Strict Env Mode вырезать переменную кэша.

## 3. Паттерны фронтенд-тестов: React 19, `TanStack Query` и `MSW v3`

Тестирование современного Next.js App Router и React 19 требует аккуратного обращения с асинхронными таймерами, DOM-очисткой и браузерными API:

### Ключевые решения в `apps/web`

- **Явные импорты из `'vitest'` + `afterEach(cleanup)`:** без глобальных `describe`/`it`/`expect` (`globals: false`) строгий TypeScript и Biome не требуют глобальной магии. Но `@testing-library/react` вызывает автоочистку DOM только при наличии глобального `afterEach`, поэтому `apps/web/vitest.setup.ts` явно регистрирует `afterEach(() => cleanup())`, исключая «утечку» DOM-элементов между тестами.
- **Строгий перехват сети в `MSW v3`:** в интеграционных тестах используется `server.listen({ onUnhandledFrame: 'error' })`, `server.resetHandlers()` после каждого теста и `server.close()` в `afterAll`. Любой незамоканный HTTP-вызов сразу валит тест без подвисаний.
- **Детерминированная отмена запросов при `unmount()`:** для проверки фильтрации `AbortError`/`CancelledError` в `makeQueryClient()` мы монтируем `useQuery` с незавершённым `Promise` и вызываем `unmount()`, корректно тестируя отмену сигнала без нестабильных `setTimeout`.
- **Защита `window.indexedDB` в `QueryProvider`:** `jsdom` по умолчанию не предоставляет браузерную реализацию `IndexedDB`. Явная проверка `typeof window.indexedDB !== 'undefined'` перед созданием персистера делает компонент стабильным и в SSR, и в тестах.
- **Radix UI Portals в RTL:** выпадающие меню `<Select>` и диалоги `<Dialog>` рендерятся через портал напрямую в `document.body`, за пределы контейнера теста. Поэтому запросы выполняются через `screen` + `@testing-library/user-event`.

## 4. Playwright E2E: `POM`, `test.step`, `Zero-Cruft data-testid` и масштабируемый `WebServer`

E2E-сценарии в `apps/web/e2e/` организованы по паттерну **Page Object Model (POM)**:

```text
apps/web/e2e/
├── fixtures/app.fixture.ts         # Типизированные фикстуры GuestPassPage и SystemStatusPage
├── pages/
│   ├── guest-pass.page.ts          # Инкапсулирует модалку, ввод имени/роли и отправку формы
│   └── system-status.page.ts       # Инкапсулирует матрицу capabilities, пагинацию 2-й страницы, логи
└── specs/
    └── rbac-and-observability.spec.ts # Полный RBAC + /system-status сценарий на базе test.step()
```

### Инженерные стандарты E2E-контура

1. **Политика `Zero-Cruft data-testid`:** Playwright **никогда** не ищет элементы по переведённым текстам (`"Войти"`, `"Next"`) или тегам вёрстки (`table`, `h2`), чтобы локализация и редизайн не ломали тесты. В то же время `data-testid` (`guest-pass-dialog`, `guest-pass-submit-btn`, `leaderboard-table` и др.) ставится **строго** на реально запрашиваемые в тестах элементы, без «замусоривания» JSX.
2. **Структурирование через `test.step(...)`:** каждый тест разбит на логические этапы (`Navigate to protected Knowledge Base route triggers GuestPassModal`, `Submit GuestPass form unlocks HttpOnly JWT session and article content`, `Inspect /system-status capabilities matrix, leaderboard pagination, and live telemetry events`). В HTML-отчётах CI и Trace Viewer видна прозрачная временная шкала по каждому шагу.
3. **Масштабируемые воркеры и serial-режим для stateful-сценариев:** `playwright.config.ts` задаёт `fullyParallel: true` и `...(process.env.CI ? { workers: 2 } : {})` для автоматического распараллеливания независимых спеков при росте проекта, а `test.describe.configure({ mode: 'serial' })` гарантирует последовательный порядок шагов в рамках одного stateful RBAC-флоу.
4. **Node 24 Happy Eyeballs DNS и Next.js `webServer` (`NODE_OPTIONS`):** при локальном и CI-запуске `next start` (`localhost:3000`) в паре с `apps/api` (`0.0.0.0:4000`) алгоритм Happy Eyeballs в **Node 24** сначала пробует IPv6 (`::1:4000`), вызывая `AggregateError` при одновременных rewrite-проксированиях `/api/*`. Переменная `NODE_OPTIONS: '--dns-result-order=ipv4first --no-network-family-autoselection'` в `env` веб-сервера гарантирует детерминированный IPv4-маршрут.

## 5. Вкладка Testing в IDE (`vitest.config.ts`) и интеграция в CI/CD

### Корневой конфиг проектов для Testing Explorer

Хранение отдельных `vitest.config.ts` внутри пакетов ускоряет `Turborepo --affected`, **но** расширения IDE сканируют корень репозитория. Корневой `vitest.config.ts` объединяет воркспейсы без дублирования настроек:

```ts title="vitest.config.ts"
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    projects: ['packages/*', 'apps/*'],
  },
})
```

В паре с `.vscode/extensions.json` (`vitest.explorer`, `ms-playwright.playwright`) и `.vscode/settings.json` (`playwright.config: "apps/web/playwright.config.ts"`) все unit- и интеграционные тесты `Vitest` и браузерные спеки `Playwright` видны прямо во вкладке Testing. Кроме того, `pnpm run test:coverage` (или `pnpm exec vitest run --coverage`) формирует V8 HTML/LCOV-отчёты, а `pnpm run test:ui` поднимает интерактивный Vitest UI на `http://localhost:5124/__vitest__/`.

### Интеграция в GitHub Actions CI

- **Stage 1 (`unit-tests`):** запускается параллельно с `lint`, `security` и `typecheck`, используя `prepare-codegen: "true"`, динамический `fetch-depth: '0'` с `TURBO_SCM_BASE` на PR (`turbo run test --affected`) и полный прогон `pnpm --filter @repo/api test:e2e`.
- **Stage 2 (`e2e`):** стартует после `needs: [ lint, typecheck, build ]`, восстанавливает кэш `.turbo` и бинарники браузера `~/.cache/ms-playwright` (по точной версии Playwright из `pnpm-lock.yaml`), прогоняет `pnpm --filter @repo/web test:e2e` и загружает HTML-отчёт/трейсы через `actions/upload-artifact@v7` при `if: failure()`.
