## 1. Why Modern Full-Stack Applications Need Defense-in-Depth

In typical web development, security is frequently deferred or reduced to installing default packages. However, in a monorepo architecture combining a public Next.js interface, a private NestJS API, microservices, and a PostgreSQL database, compromising a single node can jeopardize the entire system.

Our project adheres to the **Defense-in-Depth** principle:

```text
[ Browser ]
    │
    ├── (1) HTTP Security Headers (Next.js): CSP, HSTS, X-Frame-Options, nosniff
    │
    ├── (2) Edge Auth Barrier (proxy.ts): Web Crypto HMAC-SHA256 JWT verification
    │
    ├── (3) API Gateway Hardening (NestJS): Helmet + CORS whitelist + Throttler Guard
    │
    └── (4) Microservice Isolation: TCP :4001 inside an internal Docker network
```

Each tier is completely autonomous: if an attacker tries to bypass client validation, the backend Rate Limiter halts the attack; if they attempt an unauthorized iframe embed, `frame-ancestors 'none'` blocks the render.

## 2. HTTP Security Headers in Next.js 16 (`apps/web/config/security-headers.config.ts`)

Configuring `Content-Security-Policy` (CSP) in modern frameworks poses intricate architectural challenges: React Server Components, SSR hydration, theme scripts preventing FOUC (Flash of Unstyled Content), and live SSE streams all require specific allowances.

To keep the build configuration in `next.config.ts` lean and preserve clean boundaries between Next.js infrastructure config and FSD application source (`src/`), declarative generation of all security headers was extracted into a dedicated, strictly typed module outside `src/`: `apps/web/config/security-headers.config.ts`.

```typescript title="apps/web/config/security-headers.config.ts"
export function buildContentSecurityPolicy(isProduction: boolean, publicApiUrl = ''): string {
  const normalizedPublicApi = publicApiUrl.trim() ? ` ${publicApiUrl.trim()}` : ''

  // In production, internal infrastructure ports are NEVER exposed in headers.
  // In development, API ports, microservices, and HMR WebSockets (ws/wss) are enabled.
  const connectSrc = isProduction
    ? `'self' https:${normalizedPublicApi}`
    : `'self' http://localhost:4000 http://localhost:4001 http://127.0.0.1:4000 http://127.0.0.1:4001 ws: wss: https:${normalizedPublicApi}`

  // In production, 'unsafe-eval' is strictly disabled (MDX compiles to React AST without eval).
  // In development, 'unsafe-eval' is required for Next.js Fast Refresh.
  const scriptSrc = isProduction
    ? "'self' 'unsafe-inline'"
    : "'self' 'unsafe-inline' 'unsafe-eval'"

  const directives: string[] = [
    "default-src 'self'",
    `script-src ${scriptSrc}`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' blob: data: https:",
    "font-src 'self' data: https:",
    `connect-src ${connectSrc}`,
    "frame-ancestors 'none'",
    "form-action 'self'",
    "base-uri 'self'",
    "object-src 'none'",
    ...(isProduction ? ['upgrade-insecure-requests'] : []),
  ]

  return directives.join('; ').trim()
}
```

In `apps/web/next.config.ts`, attaching headers and stripping `X-Powered-By: Next.js` remains clean and minimal:

```typescript title="apps/web/next.config.ts"
import { getSecurityHeaders } from './config/security-headers.config'

const nextConfig: NextConfig = {
  poweredByHeader: false,
  // ...
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: getSecurityHeaders(),
      },
    ]
  },
}
```

### Directive Breakdown and Dev/Prod Isolation:
- **Zero Port Leakage & Zero Eval in Production:** Production strips internal ports (`:4000`, `:4001`, `localhost`) from `connect-src` and disables `'unsafe-eval'` in `script-src` (our Remark AST MDX engine never relies on `eval` or `new Function`).
- **`Cross-Origin-Opener-Policy: same-origin`:** Isolates the top-level browsing context, preventing Spectre / XS-Leaks and `window.opener` attacks.
- **`frame-ancestors 'none'` and `X-Frame-Options: DENY`:** Protect the portfolio and knowledge base from Clickjacking attacks—preventing unauthorized third-party sites from framing the application.
- **`object-src 'none'` and `base-uri 'self'`:** Completely disables legacy plugins (Flash, Java) and prevents unauthorized manipulation of `<base href="...">` tags.
- **`Strict-Transport-Security (HSTS)`:** The `max-age=63072000; includeSubDomains; preload` header is sent strictly in production and mandates HTTPS for 2 continuous years.
- **`Permissions-Policy`:** Explicitly disables browser sensors and interest cohort tracking (`camera=(), microphone=(), geolocation=(), browsing-topics=()`).

## 3. API Gateway Hardening in NestJS 12: Helmet with SSE Support

The `apps/api` service is built on NestJS 12 with Express. For standard HTTP header protection, we integrated `helmet`.

However, default `helmet()` applies `Cross-Origin-Resource-Policy: same-origin`. In our monorepo architecture where the frontend (Next.js on port `3000` or Vercel) queries the API (port `4000` or Render) and maintains an open `EventSource` connection to `@Sse('stream')`, the default policy causes browser stream blocking.

We resolved this in `apps/api/src/main.ts` alongside `trust proxy: 1` (single reverse-proxy hop for accurate IP rate limiting) and environment-strict CORS:

```typescript title="apps/api/src/main.ts"
import type { NestExpressApplication } from '@nestjs/platform-express'
import cookieParser from 'cookie-parser'
import helmet from 'helmet'

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create<NestExpressApplication>(AppModule)
  const isProduction = process.env.NODE_ENV === 'production'

  if (isProduction) {
    app.set('trust proxy', 1)
  }

  app.setGlobalPrefix('api')
  app.use(
    helmet({
      crossOriginResourcePolicy: { policy: 'cross-origin' },
      contentSecurityPolicy: false,
    }),
  )
  app.use(cookieParser())

  const webOrigin = process.env.WEB_ORIGIN ?? 'http://localhost:3000'
  const allowedOrigins = isProduction
    ? webOrigin
        .split(',')
        .map((origin) => origin.trim())
        .filter(Boolean)
    : [webOrigin, 'http://127.0.0.1:3000']

  app.enableCors({
    origin: allowedOrigins,
    credentials: true,
    methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  })

  // ...
}
```

> [!NOTE] Why `contentSecurityPolicy: false` on the API
> The NestJS backend functions as a pure REST & SSE API, returning structured JSON and event payloads. CSP is strictly designed for browser HTML rendering, making backend CSP generation redundant while frontend Next.js headers provide comprehensive protection.

## 4. Brute-Force Defense: `@nestjs/throttler`

One of the most critical access points is the guest pass and admin login modal (`GuestPassModal`). Without rate limiting, an automated script or botnet could brute-force the administrator secret (`ADMIN_SECRET_PASSCODE`).

To mitigate this risk, we implemented `@nestjs/throttler`:

### 1. Global Module Setup in `AppModule`:

```typescript title="apps/api/src/app.module.ts"
import { APP_GUARD } from '@nestjs/core'
import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler'

@Module({
  imports: [
    ThrottlerModule.forRoot([
      {
        ttl: 60000, // Sliding window: 60 seconds
        limit: 100,  // Base limit for standard API calls
      },
    ]),
    // ...
  ],
  providers: [
    {
      provide: APP_GUARD,
      useClass: ThrottlerGuard,
    },
  ],
})
export class AppModule {}
```

### 2. Strict Rate Limiting on Auth Endpoints:

In `AuthController`, both `POST /api/auth/guest-pass` and `POST /api/auth/login` enforce a strict quota of **maximum 5 requests per 60 seconds**:

```typescript title="apps/api/src/modules/auth/auth.controller.ts"
@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('guest-pass')
@HttpCode(HttpStatus.OK)
async issueGuestPass(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  // Session issuance and HttpOnly cookie generation
}

@Throttle({ default: { limit: 5, ttl: 60000 } })
@Post('login')
@HttpCode(HttpStatus.OK)
async login(
  @Body(new ZodValidationPipe(GuestPassFormSchema)) body: GuestPassFormInput,
  @Req() req: Request,
  @Res({ passthrough: true }) res: Response,
): Promise<SessionProfile> {
  return this.issueGuestPass(body, req, res)
}
```

### 3. Excluding the Persistent SSE Stream:

The continuous Server-Sent Events connection (`GET /api/telemetry/stream`) must not be severed by request throttlers, so `@SkipThrottle()` is scoped **strictly to the `streamEvents()` handler**, leaving `GET /api/telemetry/stats` protected by the global quota:

```typescript title="apps/api/src/modules/telemetry/telemetry.controller.ts"
@Controller('telemetry')
export class TelemetryController {
  @SkipThrottle()
  @Sse('stream')
  streamEvents(): Observable<MessageEvent> {
    return this.telemetryService.getEventStream()
  }
}
```

### 4. Architectural Evolution: In-Memory Throttler ➔ Distributed Redis Throttler

In the current single-instance deployment, `@nestjs/throttler` keeps IP counters inside Node.js memory. This provides nanosecond lookups and zero infrastructure overhead ($0).

However, during horizontal scaling (running multiple `apps/api` replicas behind a load balancer), instance memory is strictly isolated. To prevent adversaries from evading rate limits by spraying requests across replicas, the architecture is designed for a seamless upgrade to **Redis (Upstash / Docker)**:
- Integrates `ThrottlerStorageRedisService` over `ioredis` with sliding windows;
- All API replicas synchronize against a centralized atomic key-value store;
- Implements a **Graceful Degradation** fallback: if `REDIS_URL` is omitted, the backend falls back to local In-Memory throttling without disruption.

## 5. Security Checklist & Matrix

Our implemented defense stack achieves an **A+** grade on industry auditing standards:

| Threat Vector                | Monorepo Defense Implementation                                           | Status     |
| :--------------------------- | :------------------------------------------------------------------------- | :--------- |
| **XSS (Cross-Site Scripting)** | `HttpOnly` cookies + strict CSP `default-src 'self'`                      | 🛡️ Shielded |
| **Clickjacking**             | `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'`                     | 🛡️ Shielded |
| **Passcode Brute-Force**     | `@nestjs/throttler`: 5 attempts / 60 sec per IP + HTTP 429 Too Many Requests | 🛡️ Shielded |
| **MIME Sniffing**            | `X-Content-Type-Options: nosniff`                                          | 🛡️ Shielded |
| **Man-in-the-Middle (MitM)** | HSTS (`max-age=63072000; includeSubDomains; preload`)                      | 🛡️ Shielded |
| **Cross-Service Leakage**    | Private TCP `:4001` within internal Docker bridge networks                 | 🛡️ Shielded |
