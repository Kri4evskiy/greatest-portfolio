## 1. Как индексы работают внутри и какими бывают

Без индекса СУБД вынуждена читать всю таблицу целиком блок за блоком с диска/из буфера (**`Seq Scan` / Full Table Scan**) со сложностью $O(N)$. Для таблицы в 20 миллионов строк поиск одного пользователя превращается в чтение гигабайт данных.

**Индекс** — это отдельная вспомогательная структура данных на диске и в оперативной памяти (чаще всего сбалансированное дерево **B-Tree**), которая хранит отсортированные значения ключей и ссылки (`ctid` в PostgreSQL / PK в InnoDB) на строки основной таблицы, снижая стоимость поиска до $O(\log N)$:

```text
                       [ Корневая страница B-Tree: A..Z ]
                        /                              \
       [ Узел: A..M ]                                  [ Узел: N..Z ]
        /          \                                    /          \
[ Лист: A..F ]  [ Лист: G..M ]  ◄─── связный список ───► [ Лист: N..S ]  [ Лист: T..Z ]
   │  (ctid)       │                                        │
   └───────────────┼────────────────────────────────────────┘
                   ▼
         [ Heap / Таблица на диске ]
```

### Основные способы чтения данных планировщиком PostgreSQL

- **`Index Scan`:** поиск ключей в B-Tree + переходы в основную таблицу (Heap) за остальными колонками строки.
- **`Index Only Scan`:** идеальный случай — все нужные в `SELECT` колонки уже лежат внутри самого индекса (либо в `INCLUDE(...)`), поэтому чтение самой таблицы (Heap Fetch) вообще пропускается (при условии свежего Visibility Map от `VACUUM`).
- **`Bitmap Index Scan`:** когда индекс находит много разбросанных строк (или объединяет два индекса через `AND`/`OR`), СУБД сначала строит битовую карту страниц, а затем читает страницы таблицы последовательно, чтобы не прыгать хаотично по диску.
- **`Seq Scan`:** чтение всей таблицы подряд — **быстрее** индекса на маленьких таблицах (десятки/сотни строк) или когда запрос забирает > 15–20% всех строк таблицы.

### Типы индексов и когда какой выбирать

| Тип индекса | Под какие запросы заточен | Примеры в PostgreSQL |
| :--- | :--- | :--- |
| **B-Tree** *(по умолчанию)* | `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY`, префиксный `LIKE 'abc%'` | Почти 90% всех индексов (`email`, `created_at`, FK) |
| **Hash** | Строго только точное равенство `=` (меньше по размеру для длинных URL/UUID, но не умеет сортировать) | `CREATE INDEX ... USING hash (url)` |
| **GIN** *(Generalized Inverted)* | Поиск *внутри* составных значений: `JSONB` (`@>`), массивы (`&&`, `@>`), полнотекстовый поиск (`tsvector`) | `USING gin (payload jsonb_path_ops)` |
| **GiST** | Геоданные (PostGIS), интервалы (`daterange`, `tsrange`), `EXCLUDE`-ограничения, нечёткий поиск (`pg_trgm`) | Бронирование непересекающихся слотов дат |
| **BRIN** *(Block Range)* | Огромные append-only таблицы (логи, метрики 100M+ строк), физически отсортированные по времени вставки | `USING brin (created_at)` — весит в **1000×** меньше B-Tree |

## 2. Что индексируется АВТОМАТИЧЕСКИ в разных базах данных

Самая коварная ошибка при смене СУБД (например, переходе с MySQL на PostgreSQL или работе с Prisma) — считать, что все базы автоматически индексируют внешние ключи. Это **не так**:

| СУБД / Движок | `PRIMARY KEY` | `UNIQUE` | `FOREIGN KEY` | Другое / Примечание |
| :--- | :---: | :---: | :---: | :--- |
| **PostgreSQL** | ✅ B-Tree | ✅ B-Tree | ❌ **НЕТ** | `EXCLUDE` автоматически создаёт индекс (обычно GiST) |
| **MySQL (InnoDB)** | ✅ Clustered B-Tree *(сама таблица хранится в дереве PK)* | ✅ Secondary B-Tree | ✅ **ДА** *(создаёт вторичный индекс, если нет подходящего префиксного)* | Неявно добавляет 6-байтовый скрытый `ROW_ID`, если PK не задан |
| **Microsoft SQL Server** | ✅ Clustered *(по умолчанию)* | ✅ Nonclustered *(по умолчанию)* | ❌ **НЕТ** | Поведение Clustered/Nonclustered можно переопределить при создании |
| **Oracle Database** | ✅ *(если нет совместимого индекса)* | ✅ *(если нет совместимого индекса)* | ❌ **НЕТ** | **Критично:** без индекса на FK обновление/удаление PK родителя вешает блокировку уровня всей дочерней таблицы (`TM lock`)! |
| **SQLite** | ✅ `INTEGER PRIMARY KEY` = алиас `rowid`; остальные PK создают `sqlite_autoindex_*` | ✅ `sqlite_autoindex_*` | ❌ **НЕТ** | Таблица `WITHOUT ROWID` хранится как кластерный B-Tree по PK |
| **MongoDB (WiredTiger)** | ✅ Поле `_id` *(обязательный unique)* | ⚠️ Только если явно создать `{ unique: true }` | ❌ **НЕТ** *(ссылочные `userId` не индексируются)* | Все вторичные поля без ручного `createIndex()` сканируются через `COLLSCAN` |

> [!CAUTION]
> **Классическая ловушка Prisma + PostgreSQL:**
> При описании связи `@relation(fields: [authorId], references: [id])` в `schema.prisma` **PostgreSQL не создаст индекс на `authorId` автоматически** (и Prisma не добавляет его сама!). Пока в таблице 1 000 строк — всё летает. Как только таблица вырастет до 500 000 строк, каждый `JOIN` и каждое удаление родителя с `onDelete: Cascade` превращается в тяжёлый `Seq Scan` по всей таблице. Всегда добавляйте `@@index([authorId])` явно!

```prisma title="Правильное объявление FK-индекса в Prisma (PostgreSQL)"
model ArticleComment {
  id        String   @id @default(uuid())
  authorId  String
  createdAt DateTime @default(now())

  author VisitorSession @relation(fields: [authorId], references: [id], onDelete: Cascade)

  @@index([authorId])
  @@index([authorId, createdAt])
}
```

## 3. Что индексировать ОБЯЗАТЕЛЬНО (и как проектировать составные индексы)

### Чеклист обязательных кандидатов на индекс

1. **Все внешние ключи (`FOREIGN KEY`)** в PostgreSQL, SQL Server, Oracle, SQLite (и поля-ссылки в MongoDB) — для быстрых `JOIN` и предотвращения блокировок/сканов при `DELETE`/`UPDATE` родителя.
2. **Высокоселективные колонки фильтрации (`WHERE`):** `email`, `slug`, `token_hash`, `external_id`, `tenant_id`.
3. **Колонки сортировки и курсорной (Keyset) пагинации (`ORDER BY ... LIMIT`):** например `(tenant_id, created_at DESC, id DESC)`, чтобы база брала первые 20 строк прямо с верхушки отсортированного индекса без дорогого `Sort` в памяти/на диске.
4. **Предикаты `JOIN`, `GROUP BY` и `DISTINCT`** на больших таблицах.

### Правило крайнего левого префикса и правило ESR (`Equality -> Sort -> Range`)

Порядок колонок в составном индексе `(a, b, c)` критичен. Индекс по `(a, b, c)` отсортирован сначала по `a`, внутри равных `a` — по `b`, внутри равных `(a, b)` — по `c` (как телефонный справочник: `Фамилия, Имя`):

- Работает для: `WHERE a = 1`, `WHERE a = 1 AND b = 2`, `WHERE a = 1 AND b = 2 AND c > 10`.
- **НЕ работает (или крайне неэффективен)** для: `WHERE b = 2` или `WHERE c > 10` без условия на `a`!
- **Избыточный префикс:** если у вас уже есть индекс `(a, b)`, отдельный индекс `(a)` почти всегда лишний — `(a, b)` сам закрывает запросы вида `WHERE a = 1`!

При сочетании равенства, сортировки и диапазона ставьте колонки строго в порядке **ESR**:
1. **E (Equality):** колонки с точным равенством (`status = 'OPEN'`).
2. **S (Sort):** колонки из `ORDER BY` (`created_at DESC`).
3. **R (Range):** колонки с диапазоном (`amount > 100`, `created_at >= ...`).

```sql title="ESR на практике: фильтр + сортировка"
-- Запрос:
SELECT id, title, created_at
FROM system_event_log
WHERE event_type = 'ARTICLE_VIEWED'
ORDER BY created_at DESC
LIMIT 50;

-- Идеальный индекс (Equality: event_type, Sort: created_at):
CREATE INDEX idx_event_log_type_created
  ON system_event_log (event_type, created_at DESC);
```

### Мощные специализированные техники (Partial, Covering, Functional)

1. **Partial (Частичный) индекс — экономия памяти в 10–100×:**
   Если из 10 млн заказов 99.5% уже `COMPLETED` и вы постоянно ищете только `status = 'PENDING'` или активные строки `WHERE deleted_at IS NULL`:
   ```sql
   CREATE INDEX idx_orders_pending_created
     ON orders (created_at)
     WHERE status = 'PENDING';
   ```
   Индекс хранит только 0.5% строк, помещается в RAM целиком и не замедляет вставку/обновление архивных строк.

2. **Covering (Покрывающий) индекс с `INCLUDE`:**
   Позволяет планировщику сделать `Index Only Scan`, не заглядывая в основную таблицу, и при этом не раздувает ключевое дерево сортировки:
   ```sql
   CREATE INDEX idx_articles_category_include
     ON article_metrics (category)
     INCLUDE (slug, views_count);
   ```

3. **Функциональный индекс (`Expression Index`):**
   Обычный индекс на `email` **перестаёт работать**, если написать `WHERE LOWER(email) = 'user@mail.com'`! Нужно либо хранить нормализованный email, либо создать индекс по самому выражению:
   ```sql
   CREATE UNIQUE INDEX idx_users_lower_email ON users (LOWER(email));
   ```

### Что индексировать НЕ нужно

- **Крошечные таблицы** (справочники стран, ролей, статусов на 5–500 строк) — `Seq Scan` в 1 странице RAM быстрее любого обхода B-Tree.
- **Колонки с низкой селективностью сами по себе** (`is_active: true/false`, `gender`) — если значение встречается в 40–60% строк, база всё равно выберет `Seq Scan`. Исключение: сильный перекос (например, `is_flagged = true` только у 0.1% записей — тогда делайте **Partial Index** `WHERE is_flagged = true`).
- **Длинные неиспользуемые в фильтрах поля** (`description`, `raw_html`, `stack_trace`) — они раздувают B-Tree и ломаются на лимите размера ключа.

## 4. Что будет, если проиндексировать ВСЕ поля таблицы?

Новички иногда рассуждают: *«А давайте добавим индекс на каждую колонку в модели, чтобы любые фильтры в админке летали»*. В реальном продакшене это **гарантированно ломает базу данных** сразу по 7 направлениям:

### 1. Взрывное замедление записи (Write Amplification 5–15×)
При каждом `INSERT` и `DELETE` СУБД обязана обновить **не только таблицу, но и каждое дерево индекса**. Если у таблицы 15 индексов, одна вставка строки превращается в 16 модификаций B-Tree страниц (плюс расщепление страниц — **page splits** — и конкуренция за блокировки страниц).

### 2. Отключение оптимизации HOT (Heap-Only Tuples) в PostgreSQL
В PostgreSQL существует критическая оптимизация **HOT-обновлений**: если вы делаете `UPDATE users SET last_seen_at = NOW()` и колонка `last_seen_at` **не индексирована**, а в той же 8-КБ странице таблицы есть свободное место, PostgreSQL **вообще не трогает ни один индекс таблицы**!

Как только вы проиндексировали все поля — любая модификация *любой* колонки отключает HOT и вынуждает обновлять все 15–20 индексов таблицы на каждый `UPDATE`.

### 3. Раздувание WAL-логов, репликации и исчерпание IOPS
Каждое изменение индексной страницы в PostgreSQL записывается в **Write-Ahead Log (WAL)** (причём после checkpoint туда пишется вся 8-КБ страница целиком — `full_page_writes`). Избыточные индексы умножают объём WAL в разы:
- растут счета за IOPS в облаке (AWS RDS / Neon);
- read-реплики начинают отставать (**Replication Lag**);
- дольше восстанавливаются резервные копии.

### 4. Вытеснение горячих данных из RAM (Buffer Pool Thrashing)
Совокупный размер 15 индексов легко превышает размер самой таблицы в **3–5 раз** (таблица 10 ГБ ➔ индексы 40 ГБ). Эти лишние индексные страницы при каждой записи/обновлении подгружаются в общий кэш памяти (`shared_buffers` в Postgres / `innodb_buffer_pool` в MySQL), **вытесняя оттуда действительно горячие строки таблицы**. В итоге даже быстрые запросы начинают ходить на медленный диск (cache miss).

### 5. Деградация `VACUUM` / `AUTOVACUUM` и Index Bloat
Из-за MVCC при `UPDATE`/`DELETE` в PostgreSQL старые версии строк («мёртвые кортежи») не удаляются мгновенно — за ними убирает `autovacuum`. Перед удалением мёртвого кортежа `VACUUM` обязан **просканировать каждый индекс таблицы** и вычистить ссылки на него. При большом числе индексов `autovacuum` не успевает за потоком записей ➔ таблица и индексы стремительно «распухают» (**Bloat**), а в худшем случае возникает риск **Transaction ID Wraparound**.

### 6. Удорожание планировщика (Planner Overhead) и ошибки выбора плана
Перед выполнением каждого запроса оптимизатор оценивает возможные пути доступа. Когда на таблице висят 20 пересекающихся индексов, растёт CPU-время фазы `Planning Time` (критично при 10 000+ лёгких OLTP-запросов в секунду) и повышается шанс, что устаревшая статистика `ANALYZE` заставит планировщик выбрать неоптимальный индекс.

### 7. Долгие миграции, блокировки и Deadlocks
Любой `ALTER TABLE`, `REINDEX` или `CREATE INDEX` работает тем дольше, чем больше индексов уже висит на таблице, удерживая блокировки и увеличивая окно вероятности взаимных блокировок (**Deadlocks**) при параллельных транзакциях.

## 5. Шпаргалка диагностики индексов в PostgreSQL

Перед добавлением или удалением любого индекса проверяйте реальный план и статистику использования:

```sql title="1. Реальное чтение страниц и время (ищем Seq Scan и Buffers: read)"
EXPLAIN (ANALYZE, BUFFERS)
SELECT slug, views_count
FROM article_metrics
WHERE category = 'databases-sql'
ORDER BY views_count DESC
LIMIT 20;
```

```sql title="2. Поиск «мёртвых» (ни разу не использованных) и тяжёлых индексов"
SELECT
  schemaname || '.' || relname AS table_name,
  indexrelname AS index_name,
  idx_scan AS scans_count,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelid NOT IN (SELECT conindid FROM pg_constraint WHERE conindid <> 0)
ORDER BY pg_relation_size(indexrelid) DESC;
```

```sql title="3. Сравнение размера данных таблицы и суммарного размера её индексов"
SELECT
  relname AS table_name,
  pg_size_pretty(pg_table_size(relid)) AS table_heap_size,
  pg_size_pretty(pg_indexes_size(relid)) AS total_indexes_size
FROM pg_stat_user_tables
ORDER BY pg_indexes_size(relid) DESC;
```

> [!TIP]
> **Правило гигиены индексов:** если сумма размеров индексов больше размера самой таблицы (`total_indexes_size > table_heap_size`) при активной записи — проведите аудит `pg_stat_user_indexes`: почти наверняка в таблице накопились неиспользуемые одиночные индексы, избыточные левые префиксы или пропущенные кандидаты под Partial Index.
