## 1. Огляд архітектури: що саме запущено та як з’єднаний граф

Конвеєр безперервної інтеграції описаний у `.github/workflows/ci.yml`, спирається на єдиний **Composite Action** (`.github/actions/setup-workspace/action.yml`) і граф задач у `turbo.json`. Пайплайн тригериться на `push` у `main`, `pull_request` у `main` та ручний `workflow_dispatch`, із мінімальними правами на рівні всього workflow: `permissions: contents: read`.

Замість одного довгого скрипту перевірки побудовані як **двоступеневий спрямований ациклічний граф (DAG)**, у який органічно додаються майбутні автотести:

```text
Stage 1 (Паралельний Fail-Fast та граф типів)    Stage 2 (Важкі збірки після шлюзів)
─────────────────────────────────────────────    ──────────────────────────────────
[lint] (Biome 2.6, shallow) ─────────────────┐
                                             ├──▶ [build] (Turborepo + .turbo + .next/cache)
[typecheck] (tsc + prepare-codegen) ─────────┤
                                             └──▶ [storybook] (@repo/ui build-storybook)
[security] (Compose + pnpm audit, без install) ─▶ Незалежний supply-chain шлюз

Заплановане розширення (без перебудови DAG):
[unit-tests] (Vitest) ──────────────────────────▶ Паралельно Stage 1 (поруч із lint / typecheck)
[e2e] (Playwright + Chromium) ──────────────────▶ Stage 2/3 з needs: [ lint, typecheck, build ]
```

### Профілі всіх 5 Jobs

| Job | Залежності (`needs`) | Git `fetch-depth` | Ставить `node_modules`? | Команда (`pull_request` vs `main`) |
| :--- | :--- | :--- | :--- | :--- |
| **`lint`** | — | `1` (shallow) | Так (без кодогенерації) | `pnpm run lint` (`biome check .` по всьому репозиторію за ~150 мс) |
| **`security`** | — | `1` (shallow) | **Ні** | `docker compose config --quiet` → `pnpm audit --prod --audit-level=high` |
| **`typecheck`** | — | PR: `0`, `main`: `1` | Так + `prepare-codegen` | PR: `turbo run typecheck --affected`; `main`: `pnpm run typecheck` |
| **`build`** | `lint`, `typecheck` | PR: `0`, `main`: `1` | Так | PR: `turbo run build --affected`; `main`: `pnpm run build` |
| **`storybook`** | `lint`, `typecheck` | PR: `0`, `main`: `1` | Так | PR: `turbo run build-storybook --affected`; `main`: `turbo run build-storybook` |

## 2. Чому обрано Multi-Job DAG, а не один об’єднаний «швидкий» job

Може виникнути спокуса звести всі перевірки в один монолітний job, щоб не витрачати ~15–30 секунд на підйом окремої VM (`checkout` + `setup-workspace`) для кожної задачі. Ми **свідомо відмовились** від об’єднаного джоба на користь модульного DAG із п’яти причин:

1. **Готовність до `Vitest` та `Playwright` E2E:** На найближчих етапах у CI підключаються швидкі unit-тести (`Vitest`) і важчий браузерний E2E (`Playwright` для перевірки `GuestPassModal` → `HttpOnly` кука → відкриття MDX). У модульній схемі `unit-tests` безболісно стає в Stage 1 паралельно з `typecheck`, а `e2e` — у Stage 2/3 із `needs: [ lint, typecheck, build ]` та власним кешем Chromium/БД, не сповільнюючи `lint`, `security` і `storybook`.
2. **Чітка діагностика та економія важких раннерів:** В інтерфейсі GitHub PR Checks одразу видно, *який саме контур* впав (`Lint`, `Security`, `Typecheck`, `Build` або `Storybook`), без гортання спільного логу на тисячі рядків. Пов’язані `needs: [ lint, typecheck ]` не запускають ресурсомісткі збірки Next.js та Storybook, якщо порушено форматування чи типи TypeScript.
3. **Розділення прав і профілів клонування:** Джоба `security` не встановлює `node_modules` і не виконує install-скрипти пакетів, а `lint` і `security` завантажують лише останній коміт (`fetch-depth: 1`). В одному монолітному джобі довелося б тягнути повну історію Git і повний `pnpm install` заради кожної перевірки.
4. **Гранулярні правила Branch Protection:** Кожен job стає окремою обов’язковою перевіркою (Required Status Check) на злиття в `main`.
5. **Незалежний supply-chain фідбек:** Оскільки `build` і `storybook` не заблоковані джобою `security`, при появі нового стороннього CVE інженер усе одно бачить, чи збираються його код та UI-компоненти, доки вразливість усувається паралельно.

> [!NOTE]
> **Свідомий компроміс:** У приватному проєкті з жорстко обмеженими платними хвилинами CI об’єднання швидких кроків в 1–2 джоби економить час запуску VM. У нашій архітектурі пріоритет — гнучкість під майбутні `Vitest` / `Playwright`, прозорість PR-статусів та ізоляція відповідальності.

## 3. DRY-ініціалізація воркспейсу (`.github/actions/setup-workspace/action.yml`)

Щоб не дублювати налаштування `pnpm`, `Node.js 22` та кешу стору в 4+ джобах, уся підготовка винесена в локальний **Composite Action**:

```yaml title=".github/actions/setup-workspace/action.yml"
inputs:
  prepare-codegen:
    description: Build @repo/shared-schemas and generate Prisma Client before typecheck
    required: false
    default: "false"

runs:
  using: composite
  steps:
    - name: Setup pnpm
      uses: pnpm/action-setup@v5

    - name: Setup Node.js
      uses: actions/setup-node@v6
      with:
        node-version: "22"
        cache: pnpm

    - name: Install dependencies
      shell: bash
      run: pnpm install --frozen-lockfile

    - name: Prepare generated types (@repo/shared-schemas, Prisma Client & Next.js routes)
      if: inputs.prepare-codegen == 'true'
      shell: bash
      run: |
        pnpm --filter @repo/shared-schemas build
        pnpm --filter @repo/api prisma:generate
        pnpm --filter @repo/web exec next typegen
```

Чому кожен крок налаштований саме так:

- **Суворий порядок `pnpm/action-setup@v5` до `actions/setup-node@v6`:** опція `cache: pnpm` потребує вже наявного бінарника `pnpm` для визначення шляху до стору. Версія в YAML не захардкоджена — екшен зчитує `"packageManager": "pnpm@12.18.0"` із кореневого `package.json`.
- **Мажорні версії з підтримкою Node 24:** `actions/checkout@v6`, `actions/setup-node@v6`, `actions/cache@v5` і `pnpm/action-setup@v5` позбавляють логи попереджень про застарілий Node 20.
- **`pnpm install --frozen-lockfile` *без* `--ignore-scripts`:** на відміну від фінальних Docker-образів, у CI дозволеним пакетам (`@prisma/client`, `@swc/core`, `@biomejs/biome`) потрібно виконати postinstall-білд. Безпеку забезпечує білий список `allowBuilds` у `pnpm-workspace.yaml` (за замовчуванням у pnpm 12 будь-які сторонні `postinstall`-скрипти заблоковані).
- **`LEFTHOOK: 0` та вимкнення телеметрії:** глобальні змінні `CI: true`, `LEFTHOOK: 0` (щоб скрипт `prepare` не ставив git-хуки в контейнері CI), `DO_NOT_TRACK: 1`, `TURBO_TELEMETRY_DISABLED: 1` і `NEXT_TELEMETRY_DISABLED: 1`.

## 4. `concurrency` без втрати комітів у гілці `main`

Тонкість рушія GitHub Actions: в одній `concurrency`-групі одночасно зберігається максимум **1 активний + 1 очікуючий** прогон. Якщо задати для `main` статичну групу на кшталт `ci-main` із `cancel-in-progress: false`, то при 3 швидких мерджах поспіль GitHub тихо витіснить проміжний коміт із черги.

Наше рішення одночасно ізолює PR і гарантує 100% аудит на `main`:

```yaml title=".github/workflows/ci.yml"
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- **Ізоляція Pull Request:** PR #12 (`CI-12`) та PR #13 (`CI-13`) працюють у різних групах. Новий коміт у PR #12 скасовує лише старий прогон усередині PR #12.
- **Повний аудит на `main`:** кожен мердж у `main` (і ручний `workflow_dispatch`) отримує унікальний `github.run_id` із `cancel-in-progress: false` — жоден коміт не загубиться без перевірки.

## 5. `Turborepo --affected` та динамічний `fetch-depth` замість `paths:`

Фільтри `paths:` у GitHub Actions породжують дві класичні проблеми в монорепозиторіях:

1. **Блокування Branch Protection:** пропущена через `paths:` обов’язкова перевірка залишає PR у нескінченному стані _Waiting for status to be reported_.
2. **Сліпі зони спільних контрактів:** зміна схеми у `packages/shared-schemas` може зламати `apps/api`, `apps/telemetry-ms` або `apps/web`, якщо покладатися на ручні шляхи.

Натомість усі джоби стартують завжди, а `typecheck`, `build` і `storybook` використовують граф `Turborepo --affected` на PR у парі з динамічним `fetch-depth: ${{ github.event_name == 'pull_request' && 0 || 1 }}`:

- **Зміни лише в `apps/api/**`:** перевіряється і збирається **виключно `@repo/api`**; `web` та `storybook` пропускаються за ~1 секунду з чесним кодом `0` (`Success`).
- **Зміни в `packages/shared-schemas/**`:** Turborepo автоматично обчислює споживачів і перевіряє `@repo/shared-schemas`, `@repo/api`, `@repo/telemetry-ms` та `@repo/web`.
- **Зміни в `packages/ui/**`:** перезбираються `@repo/ui` (`build-storybook`) і `@repo/web`, не чіпаючи бекенд.
- **Кореневі конфіги (`tsconfig.base.json`, `pnpm-workspace.yaml`):** оголошені в `globalDependencies` у `turbo.json`, тож при їх редагуванні перевіряється весь монорепозиторій.

> [!IMPORTANT]
> **Фікс Detached HEAD на PR (`TURBO_SCM_BASE`):** На `pull_request` екшен `actions/checkout` створює detached `HEAD` (merge-коміт PR), де присутній `origin/main` (завдяки `fetch-depth: 0`), але локальна гілка `main` відсутня. Без явної бази Turborepo попереджає `Unable to resolve base branch` і перезбирає весь монорепозиторій — тому PR-запуски в `ci.yml` явно передають `TURBO_SCM_BASE="origin/${{ github.base_ref }}"`.

## 6. Пастка `typecheck` на чистому раннері (`prepare-codegen`) і шари кешу

### Навіщо `typecheck` передає `prepare-codegen: "true"`

У `turbo.json` задача `typecheck` має `"dependsOn": ["^typecheck"]` (а не `^build`), щоб пакети перевірялися паралельно без очікування важкого збирання бандлів. На порожньому раннері після `checkout` ще немає трьох згенерованих артефактів:

1. Декларацій `packages/shared-schemas/dist/index.d.ts` (їх імпортують `api`, `telemetry-ms` та `web`).
2. Типів Prisma-моделей усередині `@prisma/client` для `apps/api`.
3. Типів маршрутів Next.js у `.next/types/*`, на які посилається `apps/web/next-env.d.ts`.

Параметр `prepare-codegen: "true"` у `typecheck` завчасно генерує ці три шари. Для джобы `build` він не потрібен: там працює `"dependsOn": ["^build"]` (спочатку збирається `@repo/shared-schemas`), а скрипт збірки `@repo/api` сам викликає `prisma generate && tsc -p tsconfig.build.json`.

### Три шари кешу та захист від Cache Poisoning

1. **Store `pnpm`:** кешується через `actions/setup-node@v6` (`cache: pnpm`) в усіх джобах зі встановленням залежностей.
2. **Артефакти Turborepo (`.turbo`):** відновлюються в `build` за ключем `${{ runner.os }}-turbo-build-${{ github.sha }}` із префіксним фолбеком `${{ runner.os }}-turbo-build-`.
3. **Кеш компілятора Next.js (`apps/web/.next/cache`):** прив’язаний до хешів `pnpm-lock.yaml` і `apps/web/**`, прискорюючи інкрементальну збірку webpack/SWC і прибираючи попередження `No build cache found`.

> [!TIP]
> **Ізоляція кешу від отруєння (Cache Poisoning):** За правилами GitHub Actions прогони на Pull Request можуть *читати* кеш гілки `main` через `restore-keys`, але **не можуть** перезаписувати кеш базової гілки. А при масштабуванні команди `.turbo` легко перевести на Vercel Remote Cache через секрети `TURBO_TOKEN` і `TURBO_TEAM` без жодної правки у графі джобів.

## 7. Supply-Chain шлюз `security` та дорожня карта розвитку

### Як влаштований незалежний шлюз `security` (без `node_modules`)

```yaml title=".github/workflows/ci.yml"
  security:
    name: Security & Infra Config
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository (shallow)
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Setup pnpm
        uses: pnpm/action-setup@v5

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"

      - name: Validate Docker Compose configuration
        run: docker compose config --quiet

      - name: Audit production dependencies
        run: pnpm audit --prod --audit-level=high
```

- **Правильний порядок перевірок:** спочатку швидка офлайн-валідація `docker compose config --quiet`, потім мережевий аудит `pnpm audit --prod --audit-level=high` — помилка реєстру чи нова вразливість не замаскує зламаний синтаксис `docker-compose.yml`.
- **Чому саме `--prod --audit-level=high`:** інструменти розробки (`Storybook`, `Vite`, `Biome`, `Turbo`) не потрапляють у фінальні продакшен-контейнери `docker/*.Dockerfile` (`pnpm prune --prod`). Фокус на `--prod` дає високе співвідношення сигнал/шум без хибних блокувань через dev-залежності, а сам аудит читає `pnpm-lock.yaml` напряму без встановлення `node_modules`.
- **Живий кейс (`GHSA-mrhx-c7xc-m3w5`):** саме ця джоба виявила High-severity вразливість DoS / Memory Exhaustion у `zod < 4.6.6`. Ми виконали контрольовану міграцію на `zod@^4.6.7` + `@hookform/resolvers@^7.0.5`, оновили `z.uuid()`, `z.iso.datetime()`, `ZodType<T>` та ліміт масиву `.max(500)`, повністю очистивши прод-граф (0 high/critical вразливостей).
- **Винятки у `pnpm 12`:** якщо колись знадобиться тимчасово задокументувати хибнопозитивний чи недосяжний advisory, у `pnpm@12.18.0` використовується верхньорівневий блок `audit.ignore` у `pnpm-workspace.yaml` (через `pnpm audit --ignore <GHSA>`), а не застарілий `auditConfig`.

### План еволюції CI/CD без переписування ядра

1. **`unit-tests` (`Vitest`) — наступний крок:** стає паралельно Stage 1 (`needs: []`) із `prepare-codegen: "true"` та `turbo run test --affected` для перевірки Zod-схем, `Zustand`-сторів і сервісів NestJS.
2. **`e2e` (`Playwright`) — слідом за unit-тестами:** підключається на `needs: [ lint, typecheck, build ]` з окремим кешем Chromium, перевіркою RBAC-сценарію (`GuestPassModal` → `HttpOnly` кука → `<Redact />`) та завантаженням трейсів/звітів по `if: failure()`.
3. **Додатковий hardening:** щотижневий `schedule:` крон у `ci.yml` + `.github/dependabot.yml` (щоб нові CVE виявлялись навіть у тижні без комітів), `persist-credentials: false` на `actions/checkout@v6` та `actionlint` усередині `lint`.
4. **Роздільний CD (Continuous Delivery):** окремі per-service деплої (`apps/web` на Vercel із Remote Cache; `apps/api` та `apps/telemetry-ms` через `docker/*.Dockerfile` із `turbo prune --docker`), щоб додавання нових `.mdx`-конспектів не перезбирало Docker-образи бекенду.
