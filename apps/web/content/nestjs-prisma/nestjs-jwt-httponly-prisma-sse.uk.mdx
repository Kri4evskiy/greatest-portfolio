## 1. Чому ми заборонили `LocalStorage` для JWT-токенів

Зберігання `accessToken` у `window.localStorage` або `sessionStorage` робить застосунок вразливим до будь-якої XSS-атаки: сторонній скрипт або скомпрометований npm-пакет може прочитати токен одним рядком `localStorage.getItem('token')`.

У нашому монорепозиторії реалізована схема **HttpOnly Cookie + Dual-Layer RBAC**:

1. При сабміті мікро-форми `POST /api/auth/guest-pass` бекенд **NestJS** створює запис `VisitorSession` у PostgreSQL через **Prisma ORM**.
2. Сервер підписує JWT та виставляє заголовок `Set-Cookie`:
   - `HttpOnly` — JavaScript у браузері фізично не бачить куку `kb_access_token` у `document.cookie`.
   - `SameSite=Lax` та `Secure` — захист від CSRF та перехоплення трафіку.
3. **Рівень 1 (Next.js Edge Proxy):** До рендеру будь-якої сторінки `/knowledge-base/*` перевіряє наявність і структуру куки на Edge.
4. **Рівень 2 (NestJS `JwtRolesGuard`):** Перевіряє криптографічний підпис JWT та роль (`USER` / `ADMIN`) при запитах до `/api/knowledge/*`.

## 2. Атомарні інкременти в `Prisma ORM` та `Server-Sent Events`

Коли тімлід відкриває статтю або натискає кнопку `Helpful`, бекенд виконує атомарний `upsert` у PostgreSQL (`Neon.tech`), що виключає стан гонитви (`race condition`):

```typescript
await this.prisma.articleMetrics.upsert({
  where: { slug },
  update: { helpfulCount: { increment: 1 } },
  create: { slug, category, viewsCount: 1, helpfulCount: 1 },
});
```

Одразу після запису `apps/api` відправляє подію по TCP (`порт 4001`) у виділений мікросервіс `apps/telemetry-ms`, а підписники ендпоінту `GET /api/telemetry/stream` (`@Sse`) миттєво бачать оновлення в живому індикаторі футера.
