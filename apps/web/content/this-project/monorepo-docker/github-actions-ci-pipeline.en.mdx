## 1. Anatomy of GitHub Actions: How Our CI/CD Is Structured

Our pipeline lives in `.github/workflows/ci.yml`, backed by one reusable **Composite Action** (`.github/actions/setup-workspace/action.yml`) and the task graph in `turbo.json`. The core mental model of GitHub Actions is simple: **every `job` boots its own fresh virtual machine (`ubuntu-latest`)** with an isolated filesystem and memory.

### Key Sections and Fields in `.github/workflows/ci.yml`

| YAML Field | Purpose and How We Use It |
| :--- | :--- |
| **`on:`** | Event triggers: `push` to `main`, `pull_request` targeting `main`, and manual `workflow_dispatch` (the *Run workflow* button in GitHub UI). |
| **`permissions:`** | Scopes the ephemeral `GITHUB_TOKEN` to least privilege: strictly `contents: read` (read repository files only, zero write/release scopes). |
| **`concurrency:`** | Controls parallel runs of the same workflow: cancels stale runs inside a PR while guaranteeing every commit on `main` completes. |
| **`env:`** | Workflow-wide environment variables (`CI: true`, `LEFTHOOK: 0`, plus `DO_NOT_TRACK`, `TURBO_TELEMETRY_DISABLED`, and `NEXT_TELEMETRY_DISABLED`). |
| **`jobs.<id>.runs-on:`** | Runner OS image selector (`ubuntu-latest`). |
| **`jobs.<id>.needs:`** | Execution dependency graph. For example, `needs: [ lint, typecheck ]` holds `build` until both upstream jobs pass. |
| **`name:` / `id:`** | `name:` sets the human-readable label in GitHub UI; `id:` assigns a step reference key for reading `${{ steps.<id>.outputs.* }}`. |
| **`if:`** | Conditional execution guard on a step or job (e.g., `if: inputs.prepare-codegen == 'true'` or `if: failure()` for uploading debug artifacts). |
| **`steps` (`uses:` vs `run:`)** | `uses:` invokes an action (from Marketplace or local `./.github/actions/...`), while `run:` executes a shell command directly on the VM. |
| **`${{ ... }}` expressions** | GitHub context variables such as `github.event_name` (`push` or `pull_request`), `github.sha`, `github.event.pull_request.base.sha`, and `runner.os`. |

### `inputs` and `outputs`: Passing Data Across Steps and Jobs

Because jobs run on separate VMs, you cannot share normal shell variables across them. GitHub Actions uses **`inputs`** and **`outputs`** instead:

1. **Inside a Composite Action (`action.yml`) — parameterizing reusable steps:**
   - **`inputs:`** — arguments passed by the caller job via `with:`. In `setup-workspace`, `prepare-codegen` (`required: false`, `default: "false"`) lets `typecheck` pass `"true"` while other jobs keep `"false"`.
   - **`outputs:`** — values emitted from a step via `$GITHUB_OUTPUT` so later steps in the same job can read them.
2. **Between separate `jobs` (across distinct VMs):**
   - To pass a short string (such as a built Docker image tag, preview URL, or `changed` flag) from `job_a` to `job_b`, declare `jobs.job_a.outputs`:
     1. A step in `job_a` with `id: meta` runs `echo "tag=v1.2.3" >> "$GITHUB_OUTPUT"`.
     2. `job_a` exposes `outputs: { tag: ${{ steps.meta.outputs.tag }} }`.
     3. `job_b` declares `needs: [ job_a ]` and reads `${{ needs.job_a.outputs.tag }}`.
   - For files or directories (such as `.next` builds or Playwright HTML traces), use **`actions/upload-artifact`** and **`actions/download-artifact`** instead of `outputs`.

> [!NOTE]
> **Three levels of reuse in GitHub Actions:** repeated step sequences belong in a **Composite Action** (`uses: ./.github/actions/...`), standard single tasks come from Marketplace (`uses: actions/checkout@v6`), and entire shared multi-job pipelines (like deployment workflows) use **Reusable Workflows** (`on: workflow_call`).

## 2. Task Graph (DAG) & Why 5 Separate Jobs Beat One Monolith

Checks are wired as a two-stage **Directed Acyclic Graph (DAG)** designed to absorb future test suites without refactoring existing gates:

```text
Stage 1 (Parallel Fail-Fast & Graph Checks)       Stage 2 (Gated Heavy Artifacts)
──────────────────────────────────────────       ───────────────────────────────
[lint] (Biome 2.6, fetch-depth: 1) ──────────┐
                                             ├──▶ [build] (Turborepo + .turbo + .next/cache)
[typecheck] (tsc + prepare-codegen) ─────────┤
                                             └──▶ [storybook] (@repo/ui build-storybook)
[security] (Compose + pnpm audit, no install) ──▶ Independent supply-chain gate

Planned Extension Slots (Zero Rewrite Needed):
[unit-tests] (Vitest) ──────────────────────────▶ Parallel in Stage 1 (alongside lint / typecheck)
[e2e] (Playwright + Chromium) ──────────────────▶ Stage 2/3 with needs: [ lint, typecheck, build ]
```

### Job Matrix & Execution Profiles

| Job | Dependencies (`needs`) | Git `fetch-depth` | Installs `node_modules`? | Execution Command (`pull_request` vs `main`) |
| :--- | :--- | :--- | :--- | :--- |
| **`lint`** | — | `'1'` (shallow) | Yes (no codegen) | `pnpm run lint` (`biome check .` across the repo in ~150 ms) |
| **`security`** | — | `'1'` (shallow) | **No** | `docker compose config --quiet` → `pnpm audit --prod --audit-level=high` |
| **`typecheck`** | — | PR: `'0'`, `main`: `'1'` | Yes + `prepare-codegen` | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run typecheck` |
| **`build`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Yes | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `pnpm run build` |
| **`storybook`** | `lint`, `typecheck` | PR: `'0'`, `main`: `'1'` | Yes | PR: `TURBO_SCM_BASE=...base.sha` + `--affected`; `main`: `turbo run build-storybook` |

### Why a Multi-Job DAG Beats One Consolidated Job

Collapsing all commands into one job saves ~15–30 seconds of per-VM bootstrap (`checkout` + `setup-workspace`), but we **deliberately rejected** the single-job shortcut for five concrete reasons:

1. **Plug-and-Play `Vitest` & `Playwright` Slots:** `unit-tests` drops cleanly into Stage 1 parallel to `typecheck`, while heavy browser `e2e` hangs off `needs: [ lint, typecheck, build ]` with its own Chromium cache and database lifecycle—never delaying `lint`, `security`, or `storybook`.
2. **Clear Fail-Fast Signals in PR Checks:** reviewers immediately see *which* domain failed (`Lint`, `Security`, `Typecheck`, `Build`, or `Storybook`) without scanning one interleaved 2,000-line log, and `needs: [ lint, typecheck ]` prevents expensive Next.js/Storybook builds from booting when types or formatting are broken.
3. **Privilege & Checkout Isolation:** `security` never downloads `node_modules` or executes third-party install scripts, and `lint`/`security` clone with `fetch-depth: 1`.
4. **Atomic Required Status Checks:** GitHub Branch Protection can require each check individually (`Security`, `Typecheck`, `Build`, `Storybook`, and future test suites).
5. **Non-Blocking Supply-Chain Visibility:** because `build` and `storybook` don't depend on `security`, a newly published upstream npm CVE still lets engineers see whether application code compiles and bundles cleanly.

## 3. DRY Environment Setup (`.github/actions/setup-workspace/action.yml`)

Every job that needs workspace dependencies invokes a single local Composite Action instead of duplicating bootstrap YAML:

```yaml title=".github/actions/setup-workspace/action.yml"
inputs:
  prepare-codegen:
    description: Build @repo/shared-schemas and generate Prisma Client before typecheck
    required: false
    default: "false"

runs:
  using: composite
  steps:
    - name: Setup pnpm
      uses: pnpm/action-setup@v5

    - name: Setup Node.js
      uses: actions/setup-node@v6
      with:
        node-version: "22"
        cache: pnpm

    - name: Install dependencies
      shell: bash
      run: pnpm install --frozen-lockfile

    - name: Prepare generated types (@repo/shared-schemas, Prisma Client & Next.js routes)
      if: inputs.prepare-codegen == 'true'
      shell: bash
      run: |
        pnpm --filter @repo/shared-schemas build
        pnpm --filter @repo/api prisma:generate
        pnpm --filter @repo/web exec next typegen
```

Why every piece is ordered this way:

- **`pnpm/action-setup@v5` runs before `actions/setup-node@v6`:** `setup-node` with `cache: pnpm` requires `pnpm` to already exist on `$PATH` to resolve the store path. Omitting a hardcoded `version:` keeps root `package.json` (`"packageManager": "pnpm@12.18.0"`) as the single source of truth.
- **Unified Node 24 Action Runtime:** `actions/checkout@v6`, `actions/setup-node@v6`, `actions/cache@v5`, and `pnpm/action-setup@v5` all execute on GitHub's modern Node 24 action runtime.
- **`pnpm install --frozen-lockfile` governed by `allowBuilds`:** unlike production multi-stage Dockerfiles (`--ignore-scripts`), CI builds approved native dependencies (`@prisma/client`, `@swc/core`, `@biomejs/biome`) strictly listed in `pnpm-workspace.yaml` `allowBuilds`, while blocking arbitrary transitive install scripts by default.
- **`LEFTHOOK: 0` & Zero Telemetry:** setting `LEFTHOOK: 0` prevents root `prepare: "lefthook install"` from touching `.git/hooks` on ephemeral CI runners.

## 4. Audit-Safe `concurrency` Without Dropping `main` History

A subtle GitHub Actions engine limit: each `concurrency` group holds **at most 1 running + 1 pending workflow run**. Using a static group like `ci-main` with `cancel-in-progress: false` silently evicts intermediate commits if 3+ PRs merge back-to-back.

```yaml title=".github/workflows/ci.yml"
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- **Isolated PR lanes:** PR #12 gets `CI-12` and PR #13 gets `CI-13`. Pushing a new commit to PR #12 cancels only outdated runs inside PR #12.
- **Zero dropped `main` audits:** pushes to `main` (and `workflow_dispatch`) resolve to unique `${{ github.run_id }}` with `cancel-in-progress: false`, ensuring every merged commit finishes full verification.

## 5. With `Turborepo` vs Without It: Graph `--affected`, `fetch-depth`, and `TURBO_SCM_BASE`

### Comparing Monorepo CI Strategies

| Approach | How It Works | Trade-offs & Traps |
| :--- | :--- | :--- |
| **Single-repo / plain `pnpm -r`** | Builds and checks every workspace package unconditionally on every commit. | CI duration scales linearly; editing an `.mdx` note forces full backend rebuilds. |
| **GitHub Actions `paths:` filters** | Skips entire jobs when configured directory globs didn't change. | Deadlocks required Branch Protection checks in _Waiting_; easy to miss cross-package breaks from `packages/shared-schemas`. |
| **`Turborepo --affected` (Our Setup)** | Every job starts cleanly, and `Turborepo` inspects Git diffs + dependency edges to skip unaffected packages with exit `0`. | Requires Git history (`fetch-depth: '0'`) and an explicit PR base commit (`TURBO_SCM_BASE`). |

How `--affected` behaves on Pull Requests:
- **`apps/api/**` changed:** Turborepo checks & builds **only `@repo/api`**; `@repo/web` and `@repo/ui` skip in ~1s with clean `Success`.
- **`packages/shared-schemas/**` changed:** Turborepo traverses reverse dependents and validates `@repo/shared-schemas`, `@repo/api`, `@repo/telemetry-ms`, and `@repo/web`.
- **`packages/ui/**` changed:** rebuilds both `@repo/ui` (`build-storybook`) and `@repo/web`; backend apps stay untouched.
- **Root configs (`tsconfig.base.json`, `pnpm-workspace.yaml`):** listed under `globalDependencies` in `turbo.json`, triggering full workspace verification.

> [!IMPORTANT]
> **Two Essential GitHub Actions Rules for `--affected`:**
> 1. **Quote `'0' || '1'` in `fetch-depth`:** in GitHub Actions expressions, numeric `0` is **falsy**, so `cond && 0 || 1` always evaluates to `1` (shallow clone). Using string `'0'` (`fetch-depth: ${{ github.event_name == 'pull_request' && '0' || '1' }}`) preserves full history on PRs and fast depth `1` on `main`.
> 2. **Pass `TURBO_SCM_BASE="${{ github.event.pull_request.base.sha }}"`:** on `pull_request` events, `actions/checkout` fetches only `refs/pull/<n>/merge` in detached `HEAD`—neither local `main` nor `origin/main` exists on the runner. Providing the PR base commit SHA directly gives Turborepo an exact comparison base with zero extra `git fetch` calls.

*(On `main`, `--affected` is intentionally disabled so the production branch always verifies the full graph—accelerated by `.turbo` caching: `.md` doc changes hit `FULL TURBO` in seconds, while `.mdx` edits inside `apps/web/content/` rebuild only `@repo/web` with backend packages served from cache.)*

## 6. Clean-Runner `typecheck` (`prepare-codegen`) & Three-Layer Caching

### Why `typecheck` Sets `prepare-codegen: "true"`

In `turbo.json`, `typecheck` declares `"dependsOn": ["^typecheck"]` instead of `"^build"` so packages typecheck in parallel rather than waiting for full bundles. Right after `git checkout`, three generated type layers referenced by `tsconfig` are missing:

1. `packages/shared-schemas/dist/index.d.ts` (consumed by `api`, `telemetry-ms`, and `web`).
2. `@prisma/client` generated runtime and model types imported by `apps/api`.
3. `.next/types/*` route types referenced by `apps/web/next-env.d.ts`.

Setting `prepare-codegen: "true"` generates those three artifacts before `turbo run typecheck` starts. The `build` job needs `"false"` because `"dependsOn": ["^build"]` builds `@repo/shared-schemas` first and `@repo/api`'s build script runs `prisma generate && tsc -p tsconfig.build.json`.

### Three Cache Layers & Cache-Poisoning Isolation

1. **pnpm Store:** cached via `actions/setup-node@v6` (`cache: pnpm`) across all workspace-installing jobs.
2. **Turborepo Task Outputs (`.turbo`):** restored in `build` using `${{ runner.os }}-turbo-build-${{ github.sha }}` with prefix fallback `${{ runner.os }}-turbo-build-`.
3. **Next.js Compiler Cache (`apps/web/.next/cache`):** keyed by `pnpm-lock.yaml` and `apps/web/**` hashes to preserve incremental webpack/SWC compilation artifacts across runs.

> [!TIP]
> **Built-in Cache Security:** GitHub Actions isolates cache write scopes by branch—Pull Requests can *read* `main`'s `.turbo` and `.next/cache` via `restore-keys`, but cannot overwrite `main`'s cache entries (preventing untrusted PR cache poisoning). Adding `TURBO_TOKEN` and `TURBO_TEAM` secrets switches `.turbo` seamlessly to Vercel Remote Cache with zero DAG edits.

## 7. Supply-Chain `security` Gate & Extension Roadmap

### Why `security` Runs Isolated Without `node_modules`

```yaml title=".github/workflows/ci.yml"
  security:
    name: Security & Infra Config
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository (shallow)
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Setup pnpm
        uses: pnpm/action-setup@v5

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"

      - name: Validate Docker Compose configuration
        run: docker compose config --quiet

      - name: Audit production dependencies
        run: pnpm audit --prod --audit-level=high
```

- **Supply-Chain Isolation:** many npm compromises happen via malicious install scripts or vulnerable transitive packages. Running `security` **without `pnpm install` (`node_modules`)** inspects `pnpm-lock.yaml` directly without executing third-party code or wasting install time.
- **Fail-order discipline:** `docker compose config --quiet` executes *before* `pnpm audit` so a broken Compose topology or env interpolation error is caught offline even if npm advisory lookups fail.
- **Why `--prod --audit-level=high`:** `devDependencies` (Storybook, Vite, Biome, Turborepo) never ship inside our `docker/*.Dockerfile` runtime images (`pnpm prune --prod`). Scoping the blocking gate to `--prod` maximizes signal-to-noise without false alarms from build-only tooling.
- **Documented Exceptions in `pnpm 12`:** if an unreachable false-positive advisory ever needs a temporary documented suppression, `pnpm@12.18.0` configures `audit.ignore` at the top level of `pnpm-workspace.yaml` (via `pnpm audit --ignore <GHSA>`).

### Evolution Roadmap (Zero DAG Rewrite)

1. **`unit-tests` (`Vitest`):** parallel Stage 1 job (`needs: []`) with `prepare-codegen: "true"`, `fetch-depth: '0'` + `TURBO_SCM_BASE` on PRs, and `turbo run test --affected` to cover Zod schemas, `Zustand` stores, and `NestJS` services.
2. **`e2e` (`Playwright`):** Stage 2 job (`needs: [ lint, typecheck, build ]`) caching Chromium browsers, verifying `GuestPassModal` → `HttpOnly` JWT cookie → `.mdx` unlock & `<Redact />` flows, and uploading trace artifacts on `failure()`.
3. **Additional Hardening:** weekly `schedule:` cron for `security` + `.github/dependabot.yml` (catching CVEs between commits), `persist-credentials: false` on `actions/checkout@v6`, and `actionlint` inside `lint`.
4. **Decoupled Continuous Deployment (CD):** separate per-service CD workflows (`apps/web` to Vercel with Remote Cache; `apps/api` and `apps/telemetry-ms` via `docker/*.Dockerfile` + `turbo prune --docker`) so editing `.mdx` notes never rebuilds backend Docker images.
