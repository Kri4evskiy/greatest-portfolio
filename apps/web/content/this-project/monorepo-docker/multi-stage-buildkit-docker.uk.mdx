## 1. Тристадійний конвеєр збірки (`pruner -> builder -> runner`)

Щоб у продакшен-контейнери не потрапляли сирці, компілятори та чужі пакети монорепозиторію, кожен Dockerfile у папці `docker/` будує образ у три кроки:

1. **`pruner`:** запускає `turbo prune @repo/<app> --docker`, формуючи мінімальний підграф (`out/json/`, `out/full/`, `out/pnpm-lock.yaml`) лише для цільового сервісу.
2. **`builder`:** активує `pnpm@12.18.0`, ставить залежності через `--frozen-lockfile --ignore-scripts` зі спільним кешем BuildKit, запускає `pnpm turbo run build --filter=@repo/<app>...` та очищає `devDependencies`.
3. **`runner`:** копіює лише скомпільовані артефакти (`dist/` або `.next/standalone`) і запускає процес від непривілейованого користувача (`USER node` / `USER nextjs`).

## 2. `turbo prune` та спільний BuildKit Cache Mount

При збірці декількох мікросервісів з одного монорепозиторію `out/json/` стабілізує Docker-шар залежностей, а монтування `/root/.local/share/pnpm/store` через BuildKit `type=cache,id=pnpm` дозволяє завантажити спільні пакети один раз і перевикористати їх у всіх образах:

```dockerfile title="docker/api.Dockerfile"
FROM node:22-alpine AS pruner
RUN apk add --no-cache libc6-compat openssl
ENV DO_NOT_TRACK=1
ENV TURBO_TELEMETRY_DISABLED=1
RUN npm install -g turbo@^2
WORKDIR /app
COPY . .
RUN turbo prune @repo/api --docker

FROM node:22-alpine AS builder
RUN apk add --no-cache libc6-compat openssl
ENV DO_NOT_TRACK=1
ENV TURBO_TELEMETRY_DISABLED=1
RUN corepack enable && corepack prepare pnpm@12.18.0 --activate && pnpm --version
WORKDIR /app

COPY --from=pruner /app/out/json/ .
COPY --from=pruner /app/out/pnpm-lock.yaml ./pnpm-lock.yaml
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile --ignore-scripts
```

## 3. Очищення `devDependencies` і збереження `.prisma/client`

У стадії `builder` команда `pnpm turbo run build --filter=@repo/api...` спершу генерує Prisma-клієнт і компілює TypeScript. Перед викликом `pnpm prune --prod --ignore-scripts` згенеровані артефакти `.prisma` і `@prisma/client` тимчасово зберігаються в `/tmp` та повертаються назад після очищення, щоб бінарний рушій Prisma точно залишився у фінальному образі:

```dockerfile title="docker/api.Dockerfile"
RUN --mount=type=cache,id=pnpm,target=/root/.local/share/pnpm/store \
    pnpm turbo run build --filter=@repo/api... && \
    cp -R /app/node_modules/.pnpm/@prisma+client*/node_modules/.prisma /tmp/.prisma && \
    cp -R /app/node_modules/.pnpm/@prisma+client*/node_modules/@prisma/client /tmp/prisma-client && \
    pnpm prune --prod --ignore-scripts && \
    cp -R /tmp/.prisma /app/node_modules/.pnpm/@prisma+client*/node_modules/ && \
    cp -R /tmp/prisma-client/* /app/node_modules/.pnpm/@prisma+client*/node_modules/@prisma/client/ && \
    rm -rf /tmp/.prisma /tmp/prisma-client
```

### Характеристики фінальних продакшен-образів

| Контейнер | Базовий образ | Експонований порт | Користувач рантайму |
| :--- | :---: | :---: | :---: |
| `workfolio-telemetry-ms` | `node:22-alpine` | `4001` (лише внутрішня мережа) | `node` (не-root) |
| `workfolio-api` | `node:22-alpine` | `4000` | `node` (не-root) |
| `workfolio-web` (`standalone`) | `node:22-alpine` | `3000` | `nextjs` (`UID 1001`) |

> [!TIP]
> Оскільки продакшен-образ `api` не містить `Prisma CLI`, міграції схеми БД (`prisma migrate deploy`) виконуються окремим кроком у CI/CD перед перемиканням трафіку.
